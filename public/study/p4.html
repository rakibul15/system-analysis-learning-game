CHAPTER 12

Chat system

আগের design-গুলোতে client request পাঠাত, server উত্তর দিত। Chat-এ server-কেও নিজে থেকে client-কে message পাঠাতে হয়। পুরো chapter এই একটা সমস্যার চারপাশে। Rider আর merchant-এর মাঝে in-app chat বা live rider location একই ধাঁচের সমস্যা।

12.1

Scope

বইয়ের ধরে নেওয়া: one-on-one chat দ্রুত; ছোট group chat (সর্বোচ্চ ১০০ জন); online presence; একই account-এ একাধিক device; push notification; দিনে ৫ কোটি active user; শুধু text, ১ লাখ character-এর কম; chat history চিরকাল রাখা।

12.2

Polling, long polling, WebSocket

পাঠানো সহজ: client HTTP দিয়ে chat service-এ পাঠায় (keep-alive header রাখলে connection বারবার খুলতে হয় না)। গ্রহণ করাটা কঠিন, কারণ HTTP-তে client-ই শুরু করে।

উপায়কীভাবেসমস্যা
PollingClient কিছুক্ষণ পরপর জিজ্ঞেস করে: নতুন message আছে?বেশিরভাগ উত্তর "না", server resource নষ্ট
Long pollingClient request খুলে রাখে; নতুন message এলে বা timeout হলে server উত্তর দেয়, client আবার খোলেSender আর receiver আলাদা server-এ থাকতে পারে (stateless HTTP); client disconnect হল কি না বোঝা কঠিন; যে user কম chat করে তার জন্যও বারবার connection
WebSocketClient HTTP দিয়ে শুরু করে, handshake-এ upgrade হয়ে একটা স্থায়ী দুই-দিকের connectionপ্রতিটা connection server-এ ধরে রাখতে হয়; connection সামলানো কঠিন

বই WebSocket নেয়, পাঠানো আর গ্রহণ দুটোতেই। Port 80 বা 443 ব্যবহার করে বলে firewall-এও সাধারণত চলে।

নিজেকে যাচাই: long polling-এ sender আর receiver আলাদা server-এ থাকলে সমস্যা কোথায়?

Receiver-এর খোলা request যে server-এ আছে, message হয়তো এসেছে অন্য server-এ। সেই server receiver-কে সরাসরি উত্তর দিতে পারে না।

12.3

Architecture ও storage

Data দুই রকম। User profile, setting, বন্ধুর তালিকার মতো সাধারণ data relational DB-তে, replication আর sharding দিয়ে। Chat history আলাদা: পরিমাণ বিশাল (Facebook Messenger আর WhatsApp মিলে দিনে ৬০ billion message), বেশিরভাগ পড়া হয় সাম্প্রতিক message, আবার search বা jump-এর জন্য random access-ও লাগে। One-on-one-এ read-write অনুপাত প্রায় ১:১।

বই key-value store নেয়: সহজে horizontal scaling, data access-এর latency কম, আর relational DB long tail data ভালো সামলায় না (index বড় হলে random access ধীর)। Facebook Messenger HBase, Discord Cassandra ব্যবহার করে।

Message-এর ক্রম ঠিক করতে created_at যথেষ্ট নয়, কারণ দুটো message একই সময়ে তৈরি হতে পারে। তাই message ID-কে unique আর সময় অনুযায়ী sort-যোগ্য হতে হবে। নতুন message-এর ID পুরনোটার চেয়ে বড়।

Global ID

Part ২-এর Snowflake। পুরো system-এ unique।

Local sequence number

ID শুধু একটা one-on-one channel বা group-এর ভেতরে unique। বানানো সহজ, আর ক্রম তো ওই channel-এর ভেতরেই দরকার।

নিজেকে যাচাই: MySQL-এর auto_increment দিয়ে message ID কেন বানানো হয় না?

Chat history আছে NoSQL key-value store-এ, সেখানে সাধারণত auto_increment নেই। আর একটা কেন্দ্রীয় counter scale-এ bottleneck।

12.5

Message flow

ছোট group: message প্রতিটা সদস্যের নিজস্ব message sync queue-তে (inbox) copy হয়। Sync সহজ, কারণ প্রতিজন শুধু নিজের inbox দেখে। সদস্য কম হলে copy খরচ কম; WeChat এভাবে group ৫০০ জনে সীমিত রাখে। হাজার হাজার সদস্যে এটা চলে না।

12.6

Online presence

Presence server আলাদা, client-এর সাথে WebSocket-এ। Login-এ KV store-এ status = online আর last_active_at। Logout-এ offline।

সমস্যা disconnect। Mobile-এ network হামেশাই যায়-আসে; প্রতিবার offline-online দেখালে বন্ধুদের কাছে status বারবার বদলায়। সমাধান heartbeat: client ধরা যাক প্রতি ৫ সেকেন্ডে heartbeat পাঠায়; ৩০ সেকেন্ডের মধ্যে কিছু না এলে তবেই offline।

Status বন্ধুদের জানানো হয় publish-subscribe দিয়ে: প্রতিটা বন্ধু-জোড়ার একটা channel। ছোট group-এ ভালো চলে। বড় group-এ (যেমন ১ লাখ সদস্য) প্রতি বদলে ১ লাখ event যায়, তাই সেখানে user group-এ ঢুকলে বা তালিকা refresh করলে তখন status টেনে আনা হয়।

নিজেকে যাচাই: rider-এর app-এ network ১০ সেকেন্ডের জন্য গেল। Heartbeat থাকলে আর না থাকলে কী দেখাবে?

না থাকলে disconnect-এর সাথে সাথে offline, ফিরলে online: merchant-এর কাছে status কাঁপবে। Heartbeat থাকলে ৩০ সেকেন্ড অপেক্ষা, ১০ সেকেন্ডে ফিরে এলে status online-ই থাকে।

CHAPTER 13

Search autocomplete

Type করার সাথে সাথে সবচেয়ে জনপ্রিয় ৫টা মিলে যাওয়া query। Merchant panel-এ area, thana বা customer name খোঁজার suggestion একই সমস্যা, ছোট পরিসরে।

13.1

Scope ও হিসাব

বইয়ের ধরে নেওয়া: শুধু শুরু থেকে মিল (prefix), ৫টা suggestion, ক্রম historical query frequency দিয়ে, spell check নেই, শুধু ছোট হাতের ইংরেজি, দিনে ১ কোটি active user। উত্তর ১০০ ms-এর মধ্যে, নইলে type করতে আটকায়।

হিসাবকীভাবেফল
QPS10M × 10 search × 20 অক্ষর ÷ 86,400≈ 24,000
Peak QPS2 × QPS≈ 48,000
দিনে নতুন data (২০% query নতুন)10M × 10 × 20 byte × 20%≈ 0.4 GB

প্রতিটা অক্ষর type করলে একটা request যায়, তাই ২০ অক্ষরের query = ২০টা request।

13.2

Trie ও top-k cache

সহজ উপায়: frequency table-এ WHERE query LIKE 'prefix%' ORDER BY frequency DESC LIMIT 5। ছোট data-য় চলে, বিশাল data-য় database bottleneck। তাই trie: tree, যেখানে root খালি আর প্রতিটা node একটা অক্ষর জোড়ে। Query শেষ হওয়া node-এ frequency থাকে।

ধাপOptimization ছাড়াOptimization সহ
Prefix node খোঁজাO(p)O(1) — prefix-এর দৈর্ঘ্যে সীমা (যেমন ৫০)
Subtree ঘুরে সব queryO(c)O(1) — প্রতিটা node-এ top-k cache
Sort করে top kO(c log c)

দাম: প্রতিটা node-এ top query রাখতে অনেক বেশি জায়গা। কিন্তু ১০০ ms-এর শর্তে দ্রুত উত্তর জায়গার চেয়ে বেশি দামি।

নিজেকে যাচাই: top-k cache থাকলে একটা query-র frequency বাড়লে কী কী update করতে হয়?

শুধু শেষ node নয়, root পর্যন্ত প্রতিটা পূর্বপুরুষ node-এর cache, কারণ সবার top তালিকায় সেটা থাকতে পারে। এই কারণেই বই real-time update এড়িয়ে নির্দিষ্ট সময় পরপর নতুন trie বানায়।

13.3

Data gathering ও query service

প্রতিটা query-তে real-time trie বদলানো ধীর, আর trending বাদে suggestion রোজ খুব একটা বদলায় না। তাই দুটো আলাদা পথ।

Query service optimizationকী করে
AJAXপুরো page refresh ছাড়া request-response
Browser cachingSuggestion অল্প সময়ে বদলায় না, তাই browser-এ রাখা; Google ১ ঘণ্টা রাখে (cache-control: private, max-age=3600)
Data samplingপ্রতিটা query log না করে প্রতি N-টার একটা; processing আর storage বাঁচে
13.4

Trie-র কাজ ও scaling

কাজকীভাবে
CreateWorker aggregated data থেকে বানায়
Updateসপ্তাহে একবার নতুন trie দিয়ে পুরনোটা বদল (পছন্দের)। একটা একটা node update ধীর, কারণ পূর্বপুরুষ সবার cache বদলাতে হয়।
Deleteঘৃণা, সহিংসতা বা বিপজ্জনক suggestion: cache-এর সামনে একটা filter layer, আর DB থেকে আলাদাভাবে মুছে ফেলা

এক server-এ trie না ধরলে shard। প্রথম চিন্তা: প্রথম অক্ষর দিয়ে ভাগ (a–m এক server, n–z আরেক; দরকারে প্রথম দুই অক্ষর)। সমস্যা হল অক্ষর সমান ভাবে আসে না: 'c' দিয়ে শুরু শব্দ 'x'-এর চেয়ে অনেক বেশি। সমাধান: historical data দেখে ভাগ করা আর একটা shard map manager যে জানে কোন prefix কোন shard-এ। যেমন 's' একাই এক shard, আর 'u' থেকে 'z' মিলে আরেকটা।

নিজেকে যাচাই: trending query (যেমন হঠাৎ কোনো খবর) সাপ্তাহিক trie-তে ধরা পড়বে না। কী করবেন?

বই wrap up-এ এটা বলে: সাম্প্রতিক query-কে বেশি ওজন দেওয়া, streaming data নিয়ে কাজ (Kafka, Spark Streaming, Storm), আর trie-র কিছু অংশ real-time update। Weekly batch এর জন্য ধীর।

CHAPTER 14

YouTube

Video upload আর stream। মূল কথা দুটো: video বিশাল আর দেখার জন্য অনেক format-এ বদলাতে হয়, আর CDN-এর খরচই এখানে সবচেয়ে বড় খরচ।

14.1

Scope ও খরচের হিসাব

বইয়ের ধরে নেওয়া: দ্রুত upload, মসৃণ streaming, video quality বদলানো যায়, infrastructure খরচ কম, high availability, scalability, reliability। Mobile, web, smart TV। দিনে ৫০ লাখ active user, প্রতিজন দিনে ৫টা video দেখে, ১০% user দিনে ১টা upload করে, গড় video 300 MB, সর্বোচ্চ ১ GB।

হিসাবকীভাবেফল
দিনে নতুন storage5M × 10% × 300 MB150 TB
দিনে CDN খরচ (US, $0.02/GB)5M × 5 × 0.3 GB × $0.02$150,000

দিনে দেড় লাখ ডলার শুধু CDN-এ। তাই deep dive-এর একটা বড় অংশ খরচ কমানো। বই নিজে কিছু বানায় না যা আগে থেকে পাওয়া যায়: blob storage আর CDN-এর জন্য cloud service (Netflix AWS, Facebook Akamai)।

14.3

Transcoding ও DAG

Raw video বিশাল (৬০ fps-এর HD এক ঘণ্টায় কয়েকশো GB)। অনেক device আর browser শুধু নির্দিষ্ট format চালায়। আর network ভালো হলে উঁচু quality, খারাপ হলে নিচু: এর জন্য একই video-র অনেক resolution লাগে। Encoding format-এর দুই অংশ: container (.avi, .mov, .mp4; video, audio, metadata রাখার বাক্স) আর codec (H.264, VP9, HEVC; compress আর decompress-এর algorithm)।

Creator-রা আলাদা আলাদা processing চায় (watermark, নিজের thumbnail, HD বা SD), তাই Facebook-এর streaming video engine-এর মতো DAG (directed acyclic graph): কাজগুলো ধাপে ভাগ, যাতে পরস্পর-নির্ভরহীন কাজ সমান্তরালে চলে।

নিজেকে যাচাই: GOP কী, আর video-কে GOP-এ ভাগ করার লাভ কী?

Group of Pictures: কয়েক সেকেন্ডের একটা টুকরো যেটা নিজে স্বাধীনভাবে চালানো যায়। GOP ধরে ভাগ করলে টুকরোগুলো সমান্তরালে upload আর transcode করা যায়, আর upload মাঝপথে ভাঙলে শুধু বাকি টুকরো আবার পাঠালেই হয়।

নিজের CDNISP-দের সাথে partnership (Netflix-এর মতো); বড় project, শুধু বিশাল scale-এ

Error দুই রকম। Recoverable (যেমন একটা segment transcode-এ fail): কয়েকবার retry, না হলে client-কে error। Non-recoverable (যেমন video format নষ্ট): কাজ বন্ধ করে error। প্রতিটা component-এর জন্য বইয়ে playbook আছে: upload error-এ retry, API server stateless তাই অন্য server, metadata cache আর DB replicated।

CHAPTER 15

Google Drive

File রাখা আর device-এর মাঝে sync। YouTube-এ data একবার লেখা হয় আর বহুবার পড়া হয়; এখানে একই file বারবার বদলায়, আর একাধিক device-এ। তাই নতুন প্রশ্ন: কতটুকু পাঠাব, আর দুজন একসাথে বদলালে কী হবে।

15.1

Scope ও হিসাব

Feature: file যোগ (drag and drop), download, device-এর মাঝে sync, revision দেখা, বন্ধুদের সাথে share, file বদলালে বা মুছলে notification। Google Docs-এর মতো একসাথে editing বাইরে। গুণ: reliability (data কখনও হারানো যাবে না), দ্রুত sync, কম bandwidth, scalability, high availability।

হিসাবকীভাবেফল

Upload QPS (১ কোটি DAU, দিনে ২টা)10M × 2 ÷ 86,400≈ 240

API তিনটা: upload (ছোট file-এ simple; বড় file বা দুর্বল network-এ resumable: আগে upload URL নেওয়া, তারপর data, ভাঙলে যেখানে থেমেছিল সেখান থেকে), download, আর revision তালিকা। সব HTTPS-এ, user authenticated।

15.2

Block server ও delta sync

এক server থেকে শুরু, জায়গা ফুরালে Amazon S3-এর মতো cloud storage (একাধিক region-এ replication)। তারপর আসল কৌশল: file-কে block-এ ভাগ। প্রতিটা block সর্বোচ্চ 4 MB (Dropbox-এর মাপ), নিজস্ব hash দিয়ে চেনা যায়। Block server ভাগ করে, compress করে, encrypt করে, তারপর cloud storage-এ রাখে।

নিজেকে যাচাই: 2 GB-র একটা file-এ একটা শব্দ বদলালে delta sync ছাড়া আর সহ কতটুকু যায়?

ছাড়া পুরো 2 GB। সহ শুধু সেই শব্দ যে block-এ, সেই একটা block, সর্বোচ্চ 4 MB (compress-এর পর আরও কম)।

Metadata-য় strong consistency লাগে: একই file দুই device-এ আলাদা দেখালে বিপদ। Cache-এ invalidate on write, আর DB relational, কারণ ACID নিজে থেকেই আসে। NoSQL-এ ACID নেই, sync logic-এ আলাদা করে বানাতে হত। Table: user, device, namespace (user-এর root directory), file, file_version (প্রতিটা version শুধু-পড়া), block।

15.4

Upload, notification, conflict

Upload-এ দুটো কাজ সমান্তরালে:

  1. Metadata: client API server-কে file-এর metadata পাঠায়, DB-তে status = pending। Notification service অন্য client-দের জানায় একটা file আসছে।
  2. Content: client block server-এ পাঠায়; block server ভাগ, compress, encrypt করে cloud storage-এ। শেষ হলে cloud storage callback দেয়, API server status করে uploaded, আর notification যায়।

Download: অন্য client notification পেয়ে API server থেকে নতুন metadata আনে, তারপর block server থেকে block নামিয়ে file জোড়া লাগায়। Offline client-এর বদল offline backup queue-তে জমা থাকে।

Notification-এ long polling, WebSocket নয়। এখানে যোগাযোগ এক দিকের (server থেকে client) আর মাঝে মাঝে, chat-এর মতো দুই দিকের ঘন আদান-প্রদান নয়। Client long-poll connection খুলে রাখে; বদল এলে বা timeout হলে connection বন্ধ, client metadata এনে আবার খোলে।

Sync conflict: দুজন একই file একসাথে বদলালে যার বদল আগে process হয় সেটা জেতে। পরেরজন conflict পায়: system দুটো copy রাখে (তার local copy আর server-এর সর্বশেষ), user ঠিক করে merge করবে নাকি একটা দিয়ে অন্যটা বদলাবে।

নিজেকে যাচাই: chat-এ WebSocket নিলাম, drive-এ long polling। পার্থক্যটা এক লাইনে বলুন।

Chat-এ দুই দিকে ঘন ঘন real-time message; drive-এ শুধু server থেকে মাঝে মাঝে "কিছু বদলেছে" সংকেত, যার জন্য স্থায়ী দুই-দিকের connection অপ্রয়োজনীয়।
