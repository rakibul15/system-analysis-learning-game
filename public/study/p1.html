CHAPTER 1

শূন্য থেকে লাখো user

পুরো chapter একটা গল্প: এক server থেকে শুরু, আর প্রতিবার একটা নতুন সমস্যা দেখা দিলে একটা নতুন component যোগ। প্রতিটা component-এর জন্য মনে রাখুন: কোন সমস্যা সমাধান করে, আর কী নতুন ঝামেলা আনে।

1.1

একটা server ও request flow

শুরুতে web app, database, cache সব এক server-এ। User domain name লেখে, DNS সেটাকে IP বানায়, তারপর browser সেই IP-তে HTTP request পাঠায়।

নিজেকে যাচাই: browser কীভাবে জানে কোন server-এ request পাঠাবে?

DNS domain name থেকে IP address দেয়। সেই IP-তেই HTTP request যায়।

1.2

Web tier ও data tier আলাদা করা

User বাড়লে এক server যথেষ্ট থাকে না। প্রথম পদক্ষেপ: traffic সামলানোর server আর database-এর server আলাদা করা।

1.3

SQL বনাম NoSQL

Relational database data রাখে table আর row-তে, আর SQL দিয়ে table join করা যায়। NoSQL চার রকম, আর সাধারণত join নেই। ৪০ বছরের পুরনো আর পরীক্ষিত বলে বেশিরভাগ ক্ষেত্রে SQL-ই ভালো default।

নিজেকে যাচাই: US-Bangla-র seat booking-এ কোনটা নেবেন, কেন?

SQL। Seat, passenger, payment একে অপরের সাথে যুক্ত, আর একই seat দুজনকে বিক্রি না হওয়ার জন্য transaction লাগে।

1.4

Vertical বনাম horizontal scaling

Vertical (scale up): একই machine-এ বেশি CPU আর RAM। Horizontal (scale out): আরও machine। Traffic কম থাকলে vertical সহজ, কিন্তু এর দুটো শক্ত সীমা আছে।

1.5

Load balancer

আগের test-এ ভুল

Load balancer আসা traffic কয়েকটা web server-এ ভাগ করে দেয়। User শুধু load balancer-এর public IP জানে, server-গুলো private IP-তে থাকে। দুটো সমস্যার সমাধান হয়: কোনো server পড়ে গেলে বাকিরা traffic নেয় (failover), আর traffic বাড়লে pool-এ server যোগ করলেই চলে।

নিজেকে যাচাই: load balancer বসানোর পর web tier ঠিক হল, কিন্তু কোন অংশে এখনও failover নেই?

Data tier। Database এখনও একটাই। এর সমাধান পরের অংশের replication।

1.6

Database replication

আগের test-এ ভুল

Master database শুধু write নেয় (insert, update, delete)। Slave-রা master থেকে copy পায় আর শুধু read সামলায়। বেশিরভাগ app-এ read অনেক বেশি হয়, তাই slave সংখ্যায় বেশি থাকে।

কোনো node পড়ে গেলে কী হয়, সেটাই interview-এর আসল প্রশ্ন:

নিজেকে যাচাই: replication থাকলেও user নিজের সদ্য করা update দেখতে পাচ্ছে না, কেন?

Write master-এ গেছে, কিন্তু read আসছে এমন slave থেকে যেখানে data এখনও পৌঁছায়নি (replication lag)। সমাধান: write-এর পর কিছুক্ষণ সেই user-এর read master থেকে দেওয়া।

1.7

Cache

আগের test-এ ভুল

Cache হল memory-তে রাখা একটা অস্থায়ী store, database-এর চেয়ে অনেক দ্রুত। প্রতিবার page load-এ database-এ না গিয়ে আগে cache দেখা হয়।

Cache ব্যবহারের পাঁচটা বিবেচনা (বইয়ের সবচেয়ে গুরুত্বপূর্ণ অংশ):

বিবেচনামূল কথানা মানলে কী ভাঙে
কখন ব্যবহারRead বেশি, write কম এমন data। Memory volatile, তাই জরুরি data database-এ।Restart-এ data হারাবে
Expiration (TTL)খুব ছোটও না, খুব বড়ও নাছোট হলে DB-তে চাপ, বড় হলে stale data
ConsistencyDB আর cache-এ লেখা এক transaction-এ হয় নাদুই জায়গায় দুই রকম data
Failureএকটা cache server = SPOF; একাধিক data center-এ রাখুন, memory কিছুটা বেশি রাখুনCache পড়লে সব চাপ DB-তে
Evictionভরে গেলে কোনটা বাদ যাবে: LRU (সবচেয়ে জনপ্রিয়), LFU, FIFOনতুন data জায়গা পাবে না
নিজেকে যাচাই: TTL সমস্যা আর SPOF সমস্যার পার্থক্য কী?

TTL হল data কতক্ষণ টাটকা থাকবে সেই প্রশ্ন (stale বনাম DB-র চাপ)। SPOF হল cache server নিজেই পড়ে গেলে কী হবে সেই প্রশ্ন। আগের test-এ এই দুটো গুলিয়ে গিয়েছিল।

1.8

CDN (Content Delivery Network)

আগের test-এ ভুল

পৃথিবীজুড়ে ছড়ানো server-এর network, যা image, video, CSS, JavaScript-এর মতো static content user-এর সবচেয়ে কাছের জায়গা থেকে দেয়। User CDN server থেকে যত দূরে, page তত ধীর।

বিবেচনামূল কথা
খরচCDN data transfer-এর জন্য টাকা নেয়; কম ব্যবহৃত file CDN থেকে সরিয়ে রাখুন
Cache expiryCache-এর মতোই: খুব বড় হলে পুরনো content, খুব ছোট হলে বারবার origin থেকে আনা
CDN fallbackCDN down হলে client সমস্যাটা ধরে origin থেকে আনবে
InvalidationTTL শেষের আগে সরাতে: vendor-এর API, অথবা URL-এ version (image.png?v=2)
1.9

Stateless web tier

Web tier horizontally scale করতে হলে state (যেমন login session) web server থেকে বের করে একটা shared store-এ রাখতে হয়।

নিজেকে যাচাই: নতুন version deploy করতেই সব user logout হয়ে গেল, কারণ কী?

Session web server-এর memory-তে ছিল (stateful)। Server restart হতেই session হারিয়েছে। Session shared store-এ রাখলে এটা হত না।

1.10

একাধিক data center

User বিভিন্ন দেশে ছড়িয়ে পড়লে availability আর speed-এর জন্য একাধিক data center লাগে। geoDNS user-এর location দেখে তাকে সবচেয়ে কাছের data center-এ পাঠায়।

1.11

Message queue

Queue হল একটা durable buffer, যা asynchronous কাজ সম্ভব করে। Producer message পাঠায়, consumer নিজের সুবিধামতো তুলে নিয়ে কাজ করে। দুই পক্ষ একে অপরের জন্য অপেক্ষা করে না।

নিজেকে যাচাই: কোন কাজ queue-তে দেওয়া উচিত নয়?

যার ফল user-কে সঙ্গে সঙ্গে দিতে হবে আর যেখানে consistency জরুরি। যেমন seat খালি আছে কিনা যাচাই করে তখনই book করা।

1.12

Logging, metrics, automation

আগের test-এ ভুল

ছোট site-এ এগুলো ভালো অভ্যাস, বড় business-এ অপরিহার্য।

1.13

Database scaling ও sharding

আগের test-এ সবচেয়ে বেশি ভুল

Database scale করারও দুই উপায়। Vertical: আরও শক্তিশালী machine (AWS RDS-এ 24 TB RAM পর্যন্ত পাওয়া যায়)। কিন্তু hardware-এর সীমা আছে, SPOF-এর ঝুঁকি বেশি, আর দাম অনেক। Horizontal, মানে sharding: data ভাগ করে কয়েকটা database-এ রাখা।

কোন row কোন shard-এ যাবে, সেটা ঠিক করে hash function, যেমন user_id % 4। যে column দিয়ে ভাগ হয় তার নাম sharding key (বা partition key)।

নিজেকে যাচাই: sharding-এর তিনটা সমস্যা আর তাদের সমাধান মুখে বলুন।

① Resharding: consistent hashing। ② Celebrity/hotspot: আলাদা shard, দরকারে আরও ভাগ। ③ Cross-shard join: denormalization।

আগের test-এ ভুল

সব ধাপ একসাথে বসালে system দেখতে এমন হয়। Interview-এ "Design X" প্রশ্নে high-level diagram প্রায়ই এই কাঠামো থেকেই শুরু হয়।

সাধারণত যা বাদ পড়ে: DNS, CDN, slave database, আর নিচের logging/metrics স্তর। প্রতিটা box কোন সমস্যা সমাধান করে সেটাও পাশে লিখুন।

CHAPTER 2

মুখে মুখে হিসাব (back-of-the-envelope)

Interview-এ design টিকবে কিনা তা যাচাই করতে মোটামুটি হিসাব করতে হয়। তিনটা জিনিস মাথায় থাকলেই চলে: power of two, latency numbers, আর availability-র nine।

2.1

Power of two

1 byte = 8 bit; একটা ASCII character = 1 byte। প্রতি ২১০ ধাপে unit একটা করে বড় হয়, মানে মোটামুটি ১০০০ গুণ।

2.2

Latency numbers

Google-এর Jeff Dean-এর ২০১০ সালের সংখ্যা। Computer এখন দ্রুত হয়েছে, তাই হুবহু মুখস্থ করার দরকার নেই, কিন্তু কোনটা কোনটার চেয়ে কত গুণ ধীর, সেই অনুপাতটা আজও কাজে লাগে।

এখান থেকে যা শিখবেন

  • Memory দ্রুত, disk ধীর
  • সম্ভব হলে disk seek এড়ান
  • সাধারণ compression খুব দ্রুত
  • Internet-এ পাঠানোর আগে compress করুন
  • Data center-গুলো দূরে, তাদের মধ্যে data পাঠাতে সময় লাগে

Design-এ কোথায় লাগে

  • Hot data cache-এ রাখা (1.7)
  • User-এর কাছে CDN বা region (1.8, 1.10)
  • Response gzip/brotli করে পাঠানো
  • ঢাকার user-কে US region থেকে serve করলে প্রতিটা round trip-এ শত ms বাড়তি
2.3

Availability ও SLA

High availability মানে system দীর্ঘ সময় ধরে টানা চালু থাকা, মাপা হয় শতাংশে। SLA হল service provider আর customer-এর মধ্যে আনুষ্ঠানিক চুক্তি, কতটুকু uptime দেওয়া হবে। AWS, Google, Azure-এর SLA 99.9% বা তার বেশি। যত বেশি nine, তত কম downtime।

Availabilityদিনেসপ্তাহেমাসেবছরে

নিজে বের করার সূত্র: বছরে 8,760 ঘণ্টা, দিনে 86,400 সেকেন্ড। 99.9% মানে 0.1% বন্ধ থাকার অনুমতি: 8,760 × 0.001 ≈ 8.76 ঘণ্টা। প্রতিটা বাড়তি nine-এ downtime ১০ ভাগের এক ভাগ হয়।

নিজেকে যাচাই (বইয়ের একটু বাইরে): তিনটা service পরপর নির্ভরশীল, প্রতিটা 99.9%। পুরো system কত?

গুণ হয়: 0.999 × 0.999 × 0.999 ≈ 99.7%। নির্ভরশীল অংশ যত বাড়ে, মোট availability তত কমে। এজন্যই redundancy লাগে।

2.4

উদাহরণ: Twitter-এর QPS ও storage

ধরে নেওয়া (আসল সংখ্যা নয়): মাসে 300M active user, তার 50% প্রতিদিন আসে, প্রত্যেকে দিনে গড়ে 2টা tweet করে, 10% tweet-এ media থাকে, data রাখা হয় 5 বছর।

নিজেকে যাচাই: courier app-এ 2M DAU, প্রত্যেকে দিনে 5 বার parcel track করে। গড় QPS কত?

2M × 5 = 10M request/দিন। 10M ÷ ~100,000 s ≈ 100 QPS (সঠিক ভাগে ~116)। Peak ২ গুণ ধরলে ~230।

2.5

Estimation-এর নিয়ম

ফলের চেয়ে প্রক্রিয়া বেশি গুরুত্বপূর্ণ। Interviewer দেখেন আপনি কীভাবে সমস্যা ভাঙেন।

নিয়মউদাহরণ
Round করুন, নির্ভুলতা লাগে না99,987 ÷ 9.1 → 100,000 ÷ 10 = 10,000
Assumption লিখে রাখুন"DAU = MAU-র 50% ধরলাম", পরে reference দিতে পারবেন
Unit লিখুন"5" নয়, "5 MB"। না লিখলে KB/MB/GB গুলিয়ে ১০০০ গুণ ভুল হয়
যা বেশি জিজ্ঞেস হয়QPS, peak QPS, storage, cache size, server সংখ্যা
হাতের কাছে রাখার সংখ্যা (বইয়ের বাইরে)মান
১ দিন86,400 s ≈ 10^5 s
১ মাস≈ 2.5M s

CHAPTER 3

System design interview-এর framework

এক ঘণ্টায় কেউ Google বানাবে এটা কেউ আশা করে না। Interview আসলে দুজন সহকর্মীর একসাথে একটা অস্পষ্ট সমস্যা সমাধানের অনুকরণ। চূড়ান্ত design-এর চেয়ে প্রক্রিয়া বেশি গুরুত্বপূর্ণ।

3.1

Interviewer কী খোঁজেন

ভালো signal

  • একসাথে কাজ করার দক্ষতা (collaboration)
  • চাপের মধ্যে কাজ করা
  • অস্পষ্টতা গঠনমূলকভাবে দূর করা
  • ভালো প্রশ্ন করা: অনেক interviewer এটা আলাদাভাবে দেখেন
  • নিজের design-এর পক্ষে যুক্তি, feedback গ্রহণ

Red flag

  • Over-engineering: tradeoff উপেক্ষা করে design-এর নিখুঁততা নিয়ে মেতে থাকা
  • সংকীর্ণ মানসিকতা
  • একগুঁয়েমি
  • Requirement না বুঝেই উত্তর দেওয়া
3.2

চার ধাপ ও সময় ভাগ

3.3

ধাপ ১: সমস্যা বোঝা ও scope ঠিক করা

বইয়ের Jimmy সবার আগে হাত তোলে, প্রশ্ন বোঝার আগেই উত্তর দেয়। System design-এ Jimmy হবেন না: দ্রুত উত্তরে কোনো bonus নেই, আর requirement না বুঝে design করা বড় red flag।

সবসময় যা জিজ্ঞেস করবেন

  • ঠিক কোন feature-গুলো বানাতে হবে?
  • Product-এ কতজন user?
  • কত দ্রুত scale হবে: ৩ মাস, ৬ মাস, ১ বছরে?
  • Company-র tech stack কী, কোন existing service ব্যবহার করা যায়?

News feed-এর উদাহরণ

  • Mobile, web, না দুটোই? → দুটোই
  • মূল feature? → post করা, বন্ধুদের feed দেখা
  • সাজানো কীভাবে? → নতুন আগে (reverse chronological)
  • বন্ধু সর্বোচ্চ কত? → 5,000
  • Traffic? → 10M DAU
  • Media আছে? → image ও video
3.4

ধাপ ২: high-level design ও সম্মতি

প্রথমে একটা blueprint দাঁড় করান আর interviewer-কে teammate ভেবে feedback চান। Client, API, web server, data store, cache, CDN, queue দিয়ে box diagram আঁকুন। দরকার হলে (interviewer-কে জিজ্ঞেস করে) estimation দিয়ে যাচাই করুন, আর কয়েকটা use case দিয়ে design-এর মধ্য দিয়ে হেঁটে দেখুন। News feed-এর design দুই flow-এ ভাগ হয়:

API endpoint আর DB schema এই ধাপে দেখাবেন? সমস্যার উপর নির্ভর করে। "Design Google search"-এ খুব নিচু স্তরের, কিন্তু multiplayer poker game-এর backend-এ যুক্তিসঙ্গত। Interviewer-এর সাথে কথা বলে ঠিক করুন।

3.5

ধাপ ৩: deep dive

এই ধাপে আসার আগে scope-এ একমত, blueprint আঁকা আর feedback পাওয়া হয়ে গেছে। এখন interviewer-এর সাথে ঠিক করুন কোন component সবচেয়ে গুরুত্বপূর্ণ, আর সেটার গভীরে যান। Signal দেয় না এমন খুঁটিনাটিতে সময় নষ্ট করবেন না।

3.6

ধাপ ৪: wrap up

কী নিয়ে কথা বলবেন

  • Bottleneck আর সম্ভাব্য উন্নতি। কখনো বলবেন না design নিখুঁত।
  • Design-এর সংক্ষিপ্ত recap, বিশেষ করে একাধিক সমাধান দিয়ে থাকলে
  • Error case: server failure, network loss
  • Operation: metric আর error log কীভাবে monitor করবেন, কীভাবে roll out করবেন
  • পরের scale: 1M থেকে 10M user হলে কী বদলাবেন
  • আরও সময় পেলে আর কী refine করতেন

Chapter 1 থেকে কোনটা কোথায় লাগবে

  • Bottleneck → cache (1.7), replica (1.6), sharding (1.13)
  • Error case → SPOF, failover, redundancy (1.5, 1.14)
  • Operation → logging, metrics, CI/CD (1.12)
  • পরের scale → data center, queue (1.10, 1.11)

CHAPTER 4

Rate limiter design

এটাই বইয়ের প্রথম পূর্ণাঙ্গ design প্রশ্ন, আর Chapter 3-এর ৪ ধাপ এখানে হাতে-কলমে দেখানো হয়েছে। মূল কাজ: নির্দিষ্ট সময়ে client কতগুলো request পাঠাতে পারবে তা ঠিক করে দেওয়া, আর সীমা ছাড়ালে বাড়তি call আটকে দেওয়া।

4.1

Rate limiter কী করে, আর কেন লাগে

উদাহরণ: সেকেন্ডে ২টার বেশি post নয়, একই IP থেকে দিনে ১০টার বেশি account নয়, একই device থেকে সপ্তাহে ৫ বারের বেশি reward নয়। সীমা ছাড়ালে server 429 ফেরত দেয়।

নিজেকে যাচাই: rate limiter আর load balancer-এর কাজ কীভাবে আলাদা?

Load balancer request গুলো server-দের মধ্যে ভাগ করে দেয় (সবগুলোই যায়)। Rate limiter ঠিক করে কোন request আদৌ যাবে কিনা।

4.2

Rate limiter কোথায় বসবে

Client-এ, server-এ, নাকি মাঝখানে একটা আলাদা স্তরে, এই প্রশ্নটা Step 2-এর শুরুতেই আসে।

4.3

Token bucket

সবচেয়ে বেশি ব্যবহৃত algorithm (Amazon, Stripe)। একটা বালতিতে নির্দিষ্ট হারে token জমা হয়; প্রতিটা request একটা token খরচ করে।

মনে রাখুন: token জমে থাকে, তাই চুপচাপ থাকার পর হঠাৎ কয়েকটা request একসাথে যেতে পারে। ঈদের টিকিট বা flash sale-এর মতো burst-এ এটাই সবচেয়ে ভালো।

4.4

Leaking bucket

Token bucket-এর মতোই, তবে এখানে request একটা FIFO queue-তে জমা হয় আর স্থির হারে বেরোয় (Shopify এটা ব্যবহার করে)।

নিজেকে যাচাই: token bucket আর leaking bucket-এর মূল পার্থক্য এক লাইনে?

Token bucket burst যেতে দেয় (জমা token খরচ করে), leaking bucket সবসময় একই হারে বের করে।

4.5

Fixed window counter

সময়কে নির্দিষ্ট মাপের window-তে ভাগ করে প্রতিটার জন্য একটা counter। প্রতিটা request counter এক বাড়ায়; threshold ছুঁলে নতুন window শুরু না হওয়া পর্যন্ত বাকি request পড়ে যায়।

4.6

Sliding window log

Counter নয়, প্রতিটা request-এর timestamp জমা রাখা হয় (সাধারণত Redis-এর sorted set-এ)। নতুন request এলে পুরনো timestamp মুছে ফেলা হয়, নতুনটা যোগ হয়, তারপর log-এর আকার দেখে সিদ্ধান্ত।

4.7

Sliding window counter

আগের দুটোর মাঝামাঝি: fixed window-এর counter রাখে, কিন্তু আগের window-এর কিছু অংশ হিসাবে ধরে।

AlgorithmMemoryBurstনির্ভুলতাকখন বেছে নেবেন
Token bucketকমযেতে দেয়ভালোBurst সামলাতে হবে (flash sale)
Leaking bucketকমসমান করে দেয়ভালোপেছনের system-এ স্থির হার দরকার
Fixed windowসবচেয়ে কমপ্রান্তে ফাঁকদুর্বলসহজ নিয়ম, quota reset
Sliding window logবেশিআটকায়সবচেয়ে ভালোকড়া, নির্ভুল সীমা দরকার
Sliding window counterকমমসৃণ করেআনুমানিকবড় scale-এ ভারসাম্য
নিজেকে যাচাই: পাঁচটা algorithm-এর নাম আর এক লাইনের পার্থক্য মুখে বলুন।

Token bucket = জমা token; leaking bucket = স্থির হারে বের হওয়া queue; fixed window = window প্রতি counter; sliding window log = timestamp-এর তালিকা; sliding window counter = আগের window-এর অংশ মিলিয়ে হিসাব।

4.8

Architecture: counter, rule আর header

মূল ধারণা সহজ: একটা counter রাখো, সীমার বেশি হলে আটকে দাও। Counter database-এ নয়, in-memory cache-এ, কারণ disk ধীর আর cache-এ সময়ভিত্তিক expiration আছে।

Response headerমানে
X-Ratelimit-Limitএই window-তে সর্বোচ্চ কতগুলো call করা যাবে
X-Ratelimit-Remainingআর কতগুলো বাকি আছে
X-Ratelimit-Retry-Afterকত সেকেন্ড পর আবার চেষ্টা করা যাবে (429-এর সাথে আসে)
4.9

Distributed পরিবেশে দুটো সমস্যা

এক server-এ rate limiter বানানো কঠিন নয়। কঠিন হয় যখন অনেক server আর অনেক thread একসাথে কাজ করে।

নিজেকে যাচাই: rate limiter-এর Redis down হলে API-র কী করা উচিত?

বইয়ের requirement: rate limiter-এর সমস্যা যেন পুরো system না ফেলে। বাস্তবে আগেই ঠিক করে রাখতে হয়: সাধারণ API-তে fail open (সীমা ছাড়াই চলতে দেওয়া), আর login বা payment-এ fail closed (আটকে দেওয়া)। নাম দুটো বইয়ের বাইরে, কিন্তু interview-এ কাজে লাগে।

4.10

Wrap up: আর যা বলা যায়

বাড়তি আলোচনার বিষয়

  • Hard বনাম soft: hard-এ সীমা কখনো ছাড়ানো যায় না; soft-এ অল্প সময়ের জন্য ছাড় দেওয়া হয়
  • ভিন্ন layer: এই chapter application level (HTTP, layer 7); Iptables দিয়ে IP ধরে সীমা layer 3-এ
  • Monitoring: নিয়ম বেশি কড়া হলে বৈধ request পড়ে যাচ্ছে কিনা; হঠাৎ traffic-এ algorithm বদলানো দরকার কিনা

Client-এর best practice

  • Client cache ব্যবহার করে অপ্রয়োজনীয় call কমানো
  • সীমা জেনে সেই অনুযায়ী request পাঠানো
  • Exception বা error ধরে সামলানো
  • Retry-তে যথেষ্ট back off সময় (আর jitter) রাখা

Interview-এ পুরো উত্তরের কাঠামো: scope (client না server, কীসের ভিত্তিতে সীমা, scale, distributed কিনা) → high-level (middleware + Redis counter) → algorithm বেছে তার কারণ → deep dive (rule, 429 ও header, race condition, synchronization) → wrap up (fault tolerance, monitoring, hard/soft)।
