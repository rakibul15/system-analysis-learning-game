ভাগ ১

Data ও consistency

প্রায় প্রতিটা design সিদ্ধান্তের নিচে একটাই প্রশ্ন: কতটা পুরনো data দেখানো চলবে, আর তার বিনিময়ে কতটা গতি বা availability পাব।

7.1

CAP থেকে PACELC

CAP শুধু partition-এর সময়ের কথা বলে। কিন্তু network বেশিরভাগ সময় ঠিকই থাকে। PACELC বাকি অর্ধেকটা যোগ করে: Partition হলে A নাকি C; Else (স্বাভাবিক সময়ে) Latency নাকি Consistency।

7.2

Consistency model

"Strong" আর "eventual"-এর মাঝে কয়েকটা কাজের স্তর আছে। বেশিরভাগ product-এ পুরো strong লাগে না, এর একটা লাগে:

Modelনিশ্চয়তাকোথায় লাগে
Linearizable (strong)Write শেষ হলে সবাই সাথে সাথে নতুন মান দেখেটাকার balance, inventory-র শেষ item, lock
Read-your-writesঅন্যরা না দেখুক, আমি নিজে আমার লেখা সাথে সাথে দেখিProfile বা parcel-এর ঠিকানা edit করার পর page reload
Monotonic readsএকবার নতুন মান দেখলে আর কখনও পুরনোটা দেখব নাParcel status: "delivered" দেখার পর "in transit" ফিরে আসা চলবে না
Causalকারণ আগে, ফল পরে: comment-এর আগে post দেখা যাবেChat, comment thread
Eventualযথেষ্ট সময় পেলে সবাই একই মান দেখবেLike count, view count, analytics

Read-your-writes সহজে পাওয়ার কৌশল: write-এর পর কিছুক্ষণ সেই user-এর read primary থেকে, অথবা client শেষ write-এর version মনে রাখে আর replica সেই version পর্যন্ত না পৌঁছালে primary-তে যায়। Monotonic reads: একজন user-কে সবসময় একই replica-য় পাঠানো (sticky)।

নিজেকে যাচাই: merchant parcel-এর ঠিকানা বদলাল, save হল, কিন্তু list page-এ পুরনো ঠিকানা। কোন model ভাঙছে, সমাধান কী?

Read-your-writes। Write গেছে primary-তে, list পড়ছে পিছিয়ে থাকা replica থেকে। সমাধান: save-এর পর কয়েক সেকেন্ড ওই merchant-এর read primary থেকে, অথবা frontend-এ optimistic update দিয়ে নতুন মান দেখানো আর query invalidate (TanStack Query-তে ঠিক এটাই করেন)।

7.3

Cache pattern ও stampede

Patternকীভাবেভালোঝুঁকি
Cache-asideApp আগে cache দেখে, miss হলে DB থেকে এনে cache-এ রাখে; write-এ DB update আর cache মোছাসবচেয়ে প্রচলিত, cache পড়লেও চলেপ্রথম read ধীর; অল্প সময়ের অমিল
Write-throughপ্রতিটা write cache আর DB দুটোতে একসাথেCache সবসময় টাটকাWrite ধীর; কখনও পড়া হয় না এমন data-ও cache-এ
Write-behindWrite শুধু cache-এ, পরে batch-এ DB-তেWrite খুব দ্রুতCache পড়লে data হারায়

Cache-aside-এ write-এর সময় cache update না করে মুছে ফেলা নিরাপদ: দুটো write একসাথে এলে update-এর ক্রম উল্টে পুরনো মান cache-এ থেকে যেতে পারে, মুছলে পরের read DB থেকে ঠিক মানটা আনে।

Cache stampede: একটা খুব জনপ্রিয় key-র TTL শেষ হল, আর সেই মুহূর্তে হাজার request একসাথে miss করে DB-তে গেল। প্রতিকার: একজনকেই DB-তে যেতে দেওয়া, বাকিরা তার ফলের অপেক্ষা (request coalescing বা lock); TTL-এ একটু random যোগ (jitter), যাতে সব key একসাথে শেষ না হয়; আর মেয়াদ শেষের একটু আগেই background-এ refresh।

ভাগ ২

Service-এর গঠন

কতগুলো service, তারা কীভাবে কথা বলে, আর একটা কাজ কয়েকটা service-এ ছড়ালে সেটা কীভাবে ঠিক থাকে।

7.4

Monolith, modular monolith, microservice

MonolithModular monolithMicroservice
Deployএকটাএকটাপ্রতিটা service আলাদা
Boundaryদুর্বল, সবাই সবাইকে ছোঁয়Module-এর মাঝে স্পষ্ট interface, code-এ enforceNetwork দিয়ে বাধ্যতামূলক
Transactionসহজ, একটা DBসহজSaga, outbox, eventual consistency
Teamছোট team-এ দ্রুতমাঝারি teamঅনেক স্বাধীন team
Operation খরচকমকমবেশি: service discovery, tracing, অনেক pipeline

বাস্তব পরামর্শ: modular monolith দিয়ে শুরু, boundary পরিষ্কার রাখুন (frontend-এ Feature Sliced Design যা করে, backend-এ NestJS module একই কাজ করে)। একটা module আলাদা হওয়ার কারণ দেখা দিলে তবেই বের করুন: আলাদা scale লাগে (যেমন tracking-এর write চাপ), আলাদা team, বা আলাদা release-এর গতি। Conway's law: system-এর গঠন শেষ পর্যন্ত organization-এর যোগাযোগের গঠনের মতো হয়, তাই service-এর boundary team-এর boundary-র সাথে মেলালে ঘর্ষণ কম।

পুরনো monolith থেকে বের হওয়ার নিরাপদ পথ strangler fig: সামনে একটা routing layer, নতুন feature নতুন service-এ, পুরনো feature একটা একটা করে সরানো, শেষে monolith খালি হয়ে বন্ধ।

নিজেকে যাচাই: "microservice মানে প্রতিটা service-এর আলাদা DB" — এটা না মানলে কী সমস্যা?

দুই service একই table ছুঁলে একজনের schema বদল অন্যজনকে ভাঙে, আর কে data-র মালিক বোঝা যায় না। ফলে "distributed monolith": microservice-এর সব খরচ, কিন্তু স্বাধীনতা নেই। তবে Part ৬-এর hotel chapter মনে রাখুন: একসাথে বদলাতে হয় এমন data এক service-এ রাখাই প্রায়ই ঠিক boundary।

7.5

Sync বনাম async

Synchronous (REST, gRPC)

Caller উত্তরের অপেক্ষা করে। সহজ, debug সহজ, সাথে সাথে ফল। কিন্তু chain-এর একটা service ধীর বা বন্ধ হলে পুরোটা আটকায়; availability গুণ হয়: ৩টা ৯৯.৯% service পরপর = প্রায় ৯৯.৭%।

Asynchronous (queue, event)

Caller message রেখে চলে যায়। Service-রা আলাদা থাকে, চাপ queue শুষে নেয়। কিন্তু ফল পরে আসে, ক্রম আর duplicate সামলাতে হয়, আর একটা request কোথায় আটকাল খুঁজতে tracing লাগে।

নিয়ম: user এখনই যার উত্তর চায় (parcel তৈরি হল কি না, দাম কত) সেটা sync; যার ফল পরে হলেও চলে (SMS পাঠানো, invoice বানানো, analytics, search index) সেটা async।

Protocolকোথায় মানায়
REST (JSON over HTTP)Public API, browser, সহজ CRUD; cache আর tooling সবচেয়ে ভালো
gRPC (Protobuf over HTTP/2)Service থেকে service; দ্রুত, typed contract, streaming; browser-এ সরাসরি কম চলে
GraphQLঅনেক রকম client যাদের আলাদা আলাদা data লাগে; over-fetching কমে। দাম: HTTP cache কঠিন, query-র খরচ নিয়ন্ত্রণ লাগে
7.6

Event-driven ও transactional outbox

Event তিন রকমভাবে ব্যবহার হয়: notification (শুধু "parcel 123 delivered হয়েছে", বিস্তারিত চাইলে API call), event-carried state transfer (event-এই দরকারি সব data, consumer নিজের copy রাখে, API call লাগে না), আর event sourcing (event-ই আসল data, Part ৬-এ দেখেছি)।

সবচেয়ে সাধারণ bug: service DB-তে লিখল, তারপর Kafka-য় event পাঠানোর আগে crash। DB-তে parcel delivered, কিন্তু কেউ জানল না: SMS গেল না, COD settlement শুরু হল না। উল্টো ক্রমে করলে event গেল কিন্তু DB-তে লেখা হল না। দুটো আলাদা system-এ একসাথে লেখা যায় না (dual write সমস্যা)।

নিজেকে যাচাই: outbox থাকলে consumer-এ idempotency আবার কেন লাগে?

Relay Kafka-য় পাঠাল, row-কে "sent" করার আগে crash। ফিরে এসে আবার পাঠাবে। Outbox হারানো ঠেকায়, duplicate ঠেকায় না। Duplicate ঠেকানো consumer-এর কাজ।

ভাগ ৩

টিকে থাকা

Distributed system-এ কিছু না কিছু সবসময় ভাঙা থাকে। প্রশ্ন হল একটা অংশের ভাঙন বাকিদের কাছে ছড়ায় কি না, আর ভাঙলে আমরা কত দ্রুত জানি।

7.7

Timeout, retry, circuit breaker

কৌশলকী করেভুল করলে
Timeoutপ্রতিটা network call-এর সর্বোচ্চ অপেক্ষাTimeout না থাকলে একটা ধীর service সব thread আটকে দেয়
Retry + backoff + jitterFail হলে আবার, প্রতিবার বেশি অপেক্ষা, সাথে random অংশJitter ছাড়া সব client একসাথে retry করে (thundering herd); non-idempotent কাজে retry মানে duplicate
Circuit breakerDownstream বারবার fail করলে কিছুক্ষণ call বন্ধ, সাথে সাথে fallbackনা থাকলে মরা service-কে retry দিয়ে আরও মারা
Bulkheadপ্রতিটা downstream-এর জন্য আলাদা connection pool বা thread poolনা থাকলে একটা ধীর dependency সব resource খেয়ে ফেলে
Load sheddingঅতিরিক্ত চাপে কম জরুরি request সাথে সাথে বাদ (429, 503)সবাইকে ধীরে সেবা দিতে গিয়ে কাউকেই না
Graceful degradationঅংশ ভাঙলে কম feature নিয়ে চলাRecommendation service পড়লে পুরো page error
7.8

Observability ও SLO

স্তম্ভউত্তর দেয়উদাহরণ
Metricsকিছু কি ভুল হচ্ছে? কতটা?Error rate, p99 latency, queue-তে জমা
Logsঠিক কী ঘটেছিল?Structured JSON log, সাথে request_id
Tracesসময়টা কোন service-এ গেল?একটা request-এর পুরো পথ, প্রতিটা hop-এর সময় (OpenTelemetry)

কী মাপবেন: request-চালিত service-এ RED (Rate, Errors, Duration); resource-এ (CPU, disk, queue) USE (Utilization, Saturation, Errors)। Latency-তে গড় নয়, percentile: গড় ১০০ ms হলেও p99 ৩ সেকেন্ড হতে পারে, আর সবচেয়ে সক্রিয় user-রাই সেই ধীর ১%-এ বেশি পড়ে।

শব্দমানেউদাহরণ
SLIযা মাপা হয়সফল tracking request-এর শতাংশ
SLOনিজেদের লক্ষ্য৩০ দিনে ৯৯.৯% সফল
SLACustomer-এর সাথে চুক্তি, ভাঙলে ক্ষতিপূরণ৯৯.৫%, SLO-র চেয়ে ঢিলা
Error budget১০০% − SLO: কতটা ভুল চলবে৩০ দিনে ~৪৩ মিনিট; ফুরালে নতুন feature থামিয়ে stability-তে কাজ
7.9

Deploy ও migration

কৌশলকীভাবেকখন
RollingServer একটা একটা করে নতুন version-এDefault; কিছু সময় দুই version একসাথে চলে
Blue-greenপুরো নতুন environment পাশে, traffic এক ধাক্কায় সরানোদ্রুত rollback দরকার; খরচ দ্বিগুণ
Canaryপ্রথমে ১–৫% traffic নতুন version-এ, metric দেখে ধীরে বাড়ানোঝুঁকিপূর্ণ পরিবর্তন
Feature flagCode deploy হয় বন্ধ অবস্থায়, পরে চালুDeploy আর release আলাদা করা; নির্দিষ্ট merchant-দের জন্য আগে চালু

Rolling বা canary-তে কিছু সময় পুরনো আর নতুন code একই database-এ চলে। তাই schema বদল হয় expand / contract-এ: (১) নতুন column যোগ, পুরনোটা রাখা; (২) code দুই জায়গাতেই লেখে; (৩) পুরনো data নতুন column-এ copy; (৪) code শুধু নতুনটা পড়ে; (৫) সব ঠিক থাকলে পুরনো column মোছা। প্রতিটা ধাপ আলাদা deploy, আর প্রতিটা ধাপে rollback সম্ভব।

নিজেকে যাচাই: column-এর নাম phone থেকে msisdn করতে একটা migration-এ rename করলে কী ভাঙবে?

Rolling deploy-এর সময় পুরনো server-রা এখনও phone খুঁজবে, পাবে না, error। আর rollback করলে নতুন column নামে data, পুরনো code পড়তে পারে না। Expand/contract-এ দুই নাম কিছু সময় পাশাপাশি থাকে।

API design

Offset pagination

?page=50&size=20। সহজ, যেকোনো page-এ লাফ দেওয়া যায়। কিন্তু অনেক গভীরে DB-কে আগের সব row গুনতে হয় (ধীর), আর মাঝে নতুন row ঢুকলে item বাদ পড়ে বা দুবার আসে।

Cursor pagination

?after=parcel_98231&size=20। Index ধরে সরাসরি পরের অংশ, যত গভীরেই হোক দ্রুত, আর নতুন row-এ ক্রম ভাঙে না। দাম: নির্দিষ্ট page নম্বরে লাফ দেওয়া যায় না। Infinite scroll আর বড় list-এ এটাই।

7.11

Security-র মূল কথা

বিষয়মূল কথা
Authentication বনাম authorizationপ্রথমটা "আপনি কে", দ্বিতীয়টা "আপনি এটা করতে পারেন কি না"। দ্বিতীয়টা প্রতিটা resource-এ server-এ যাচাই: merchant A যেন merchant B-র parcel না দেখে (IDOR)
Session বনাম JWTSession: server-এ state, সাথে সাথে বাতিল করা যায়। JWT: stateless, যাচাই দ্রুত, কিন্তু মেয়াদের আগে বাতিল কঠিন। তাই ছোট মেয়াদের access token + লম্বা মেয়াদের refresh token
OAuth 2.0 / OIDCOAuth অনুমতি দেওয়ার জন্য (তৃতীয় পক্ষ আমার data পড়বে), OIDC তার উপর login। SPA আর mobile-এ PKCE সহ authorization code flow
Token রাখা (browser)httpOnly, Secure, SameSite cookie: JavaScript পড়তে পারে না, তাই XSS-এ চুরি কঠিন। localStorage-এ রাখলে যেকোনো XSS token নিয়ে যায়
Least privilegeপ্রতিটা service আর মানুষ শুধু যতটুকু দরকার ততটুকু অনুমতি
SecretsCode বা repo-তে নয়; secret manager-এ, নিয়মিত বদলানো

Performance বাজেটCore Web Vitals: LCP (প্রধান content কখন), INP (click-এর পর সাড়া), CLS (layout লাফানো)। Code splitting, image optimization, CDN, edge cache
