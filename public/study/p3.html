CHAPTER 8

URL shortener

লম্বা URL দিলে ছোট একটা alias ফেরত, আর সেই alias-এ click করলে আসল URL-এ redirect। SMS-এ parcel tracking link পাঠানোর সময় প্রতিটা character-এর দাম আছে, তাই এই সমস্যা delivery platform-এও আসল।

8.1

Scope ও হিসাব

বইয়ের ধরে নেওয়া: দিনে ১০ কোটি নতুন URL, short URL যত ছোট সম্ভব, শুধু সংখ্যা আর ইংরেজি অক্ষর, মুছে ফেলা বা update নেই, high availability আর fault tolerance। Read-write অনুপাত ১০:১।

হিসাবকীভাবেফল
Write / সেকেন্ড100M ÷ 24 ÷ 3600≈ 1,160
Read / সেকেন্ড1,160 × 10≈ 11,600
১০ বছরে record100M × 365 × 10365 billion
Storage (গড় URL 100 byte)365B × 100 byte≈ 365 TB
8.2

API ও 301 বনাম 302

দুটো endpoint। POST api/v1/data/shorten body-তে longUrl নিয়ে shortURL ফেরত দেয়। GET api/v1/shortUrl redirect-এর জন্য longURL ফেরত দেয়। Redirect-এর status code-টাই এখানে আসল সিদ্ধান্ত।

নিজেকে যাচাই: merchant জানতে চায় তার tracking link কতবার click হয়েছে। কোনটা নেবেন?

302। 301-এ দ্বিতীয় click থেকে browser আর server-এ আসে না, তাই গোনা যায় না।

8.3

Short URL কত লম্বা

অক্ষর পাওয়া যায় ৬২টা: 0–9 (১০টা), a–z (২৬টা), A–Z (২৬টা)। দৈর্ঘ্য n হলে মোট সম্ভাব্য URL 62n। লাগবে এমন সবচেয়ে ছোট n, যেখানে 62n ≥ 365 billion।

n62n365 billion-এর জন্য যথেষ্ট?
5≈ 916 millionনা
6≈ 56.8 billionনা
7≈ 3.5 trillionহ্যাঁ

তাই n = 7। Data model খুব সাধারণ: একটা table, তিন column: id, shortURL, longURL।

8.4

Hash + collision বনাম base 62

Hash + collision resolution

Long URL-কে CRC32, MD5 বা SHA-1 দিয়ে hash করে প্রথম ৭ অক্ষর নিন। DB-তে আগে থেকে থাকলে (collision) long URL-এর সাথে একটা নির্দিষ্ট string জুড়ে আবার hash। প্রতিবার DB-তে খোঁজা ধীর, তাই আগে bloom filter।

Base 62 conversion

Part ২-এর unique ID generator থেকে একটা সংখ্যার ID নিন, সেটাকে base 62-এ লিখুন। যেমন 11157 = 2×62² + 55×62 + 59, অক্ষরে 2TX। ID unique, তাই collision হয় না।

Hash + collisionBase 62
দৈর্ঘ্যস্থির ৭ID বাড়লে বাড়ে
Unique ID generator লাগে?নাহ্যাঁ
Collisionসম্ভব, সামলাতে হয়অসম্ভব
পরের URL অনুমান করা যায়?নাযায় (ID বাড়ে ১ করে) — security ঝুঁকি
নিজেকে যাচাই: base 62-এ পরের URL অনুমান করা গেলে সমস্যা কী?

কেউ একের পর এক short URL চালিয়ে অন্যদের link বের করে ফেলতে পারে। Tracking link-এ customer-এর ঠিকানা বা ফোন নম্বর থাকলে সেটা data leak।

8.5

পুরো flow

বই base 62 বেছে নেয়। Shorten-এর ধাপ:

  1. Long URL এল। DB-তে আগে থেকে আছে? থাকলে সেই short URL ফেরত।
  2. না থাকলে unique ID generator থেকে নতুন ID।
  3. ID-কে base 62-এ রূপান্তর করে short URL।
  4. ID, short URL, long URL দিয়ে DB-তে নতুন row।
CHAPTER 9

Web crawler

কিছু URL দিয়ে শুরু, সেই page নামানো, তার ভেতরের link বের করা, সেগুলো আবার নামানো। ব্যবহার: search engine indexing, web archive, web mining, copyright বা trademark monitoring।

9.1

Scope ও হিসাব

বইয়ের ধরে নেওয়া: search engine indexing, মাসে ১০০ কোটি page, শুধু HTML, ৫ বছর রাখা, duplicate content বাদ। সাথে চারটা গুণ: scalability, robustness (খারাপ HTML, crash করা server, ফাঁদ), politeness (এক site-এ অল্প সময়ে বেশি request নয়), extensibility (নতুন content type যোগ সহজ)।

হিসাবকীভাবেফল
QPS1B ÷ 30 ÷ 24 ÷ 3600≈ 400
Peak QPS2 × QPS≈ 800
মাসে storage (গড় page 500 KB)1B × 500 KB500 TB
৫ বছরে500 TB × 12 × 530 PB
9.2

Component ও flow

নিজেকে যাচাই: content seen check-এ পুরো HTML character ধরে তুলনা করলে সমস্যা কী?

১০০ কোটি page-এ এটা খুব ধীর আর ব্যয়বহুল। তার বদলে প্রতিটা page-এর hash রাখা হয়, আর শুধু hash মেলানো হয়।

9.3

BFS ও URL frontier

Web হল একটা directed graph: page node, link edge। DFS খুব গভীরে চলে যেতে পারে, তাই BFS (FIFO queue)। কিন্তু সাধারণ BFS-এর দুটো সমস্যা: একই page-এর বেশিরভাগ link একই host-এর, তাই একসাথে সেই host-এ বন্যা (impolite); আর সব URL-কে সমান গুরুত্ব দেয়।

নিজেকে যাচাই: politeness নিশ্চিত করতে এক host-এর সব URL একটা queue-তে রাখা কেন?

প্রতিটা queue-কে একটাই worker নামায়, আর প্রতি download-এর মাঝে delay রাখে। তাই এক host-এ একসাথে একটার বেশি request যায় না, অথচ বিভিন্ন host সমান্তরালে চলে।

CHAPTER 10

Notification system

Push, SMS আর email দিয়ে user-কে খবর পাঠানো। Delivery platform-এ এটা প্রতিদিনের কাজ: parcel pickup, out for delivery, delivered, COD জমা। Chapter-এর মূল প্রশ্ন: একটা notification-ও যেন না হারায়, আবার একই notification যেন বারবার না যায়।

10.1

Scope ও তিন ধরন

বইয়ের ধরে নেওয়া: iOS ও Android push, SMS, email; soft real-time (যত দ্রুত সম্ভব, চাপ বেশি হলে সামান্য দেরি চলে); user opt-out করতে পারে। দিনে ১ কোটি push, ১০ লাখ SMS, ৫০ লাখ email।

ধরনপথProvider-এর উদাহরণ
iOS pushProvider → APNs → iOS device; লাগে device token আর payloadApple Push Notification Service
Android pushProvider → FCM → Android deviceFirebase Cloud Messaging
SMSProvider → SMS service → phoneTwilio, Nexmo
EmailProvider → email service → inboxSendgrid, Mailchimp

Contact info যোগাড়: app install বা signup-এর সময় API server device token, ফোন নম্বর, email নিয়ে DB-তে রাখে। একজন user-এর একাধিক device থাকতে পারে, তাই user আর device আলাদা table।

10.2

প্রথম design ও তার সমস্যা

সহজ design: কয়েকটা service (billing, shipping …) একটা notification server-কে call করে, server সরাসরি APNs, FCM, SMS, email provider-কে পাঠায়। তিনটা সমস্যা:

সমস্যাকেন
Single point of failureএকটাই notification server
Scale করা কঠিনDB, cache আর notification processing সব এক জায়গায়, আলাদা করে বাড়ানো যায় না
Performance bottleneckHTML বানানো আর third-party-র উত্তরের অপেক্ষায় সময় যায়; peak-এ system ভেঙে পড়তে পারে
10.3

উন্নত design

নিজেকে যাচাই: সব ধরনের জন্য একটা queue না রেখে আলাদা কেন?

একটা provider বন্ধ বা ধীর হলে তার message queue-তে জমবে, কিন্তু অন্য ধরনের notification আটকাবে না। আর প্রতিটা ধরনের worker তার চাপ অনুযায়ী আলাদাভাবে বাড়ানো যায়।

10.4

Reliability ও বাকি অংশ

Data হারানো চলবে না

Notification দেরিতে বা ভিন্ন ক্রমে গেলেও চলে, কিন্তু হারানো চলবে না। তাই worker পাঠানোর আগে notification log DB-তে রাখে। Provider fail করলে worker message আবার queue-তে দেয় আর retry করে।

Exactly once কি সম্ভব?

না। Distributed system-এ duplicate কখনও কখনও হবেই। কমানোর উপায় dedupe: প্রতিটা event-এর একটা ID; worker আগে দেখে এই ID আগে পাঠানো হয়েছে কি না। হলে বাদ।

অংশকী করে
Templateএকই format বারবার না বানিয়ে parameter বসানো; format একরকম থাকে, ভুল কমে
Notification settingপাঠানোর আগে দেখা user ওই channel-এ opt-in কি না (user_id, channel, opt_in)
Rate limitingএকজনকে কতগুলো পাঠানো যাবে তার সীমা; বেশি গেলে user notification পুরো বন্ধ করে দিতে পারে
RetryThird-party fail করলে queue-তে ফেরত; বারবার fail হলে developer-কে alert
Securityশুধু authenticated client API call করতে পারে (appKey, appSecret)
Queue monitoringQueue-তে জমা notification বেশি হলে worker বাড়ানো
Event trackingOpen rate, click rate, engagement; analytics service-এর সাথে যুক্ত
নিজেকে যাচাই: worker SMS পাঠাল, provider সফল, কিন্তু ack আসার আগে worker crash। কী হবে, কীভাবে সামলাবেন?

Message queue-তে ফেরত যাবে আর অন্য worker আবার পাঠাতে চাইবে। Event ID দিয়ে dedupe থাকলে দ্বিতীয়বার যাবে না। এই কারণেই exactly-once-এর বদলে "at least once + dedupe"।

CHAPTER 11

News feed system

Home page-এ বন্ধুদের নতুন post-এর তালিকা। দুটো আলাদা flow: feed publishing (post লেখা হলে বন্ধুদের feed-এ পৌঁছানো) আর news feed building (feed খুললে post জোড়া লাগিয়ে দেখানো)।

11.1

Scope ও API

বইয়ের ধরে নেওয়া: web আর mobile; post দেওয়া আর বন্ধুদের post দেখা; সাজানো উল্টো সময়ক্রমে; একজনের সর্বোচ্চ ৫,০০০ বন্ধু; দিনে ১ কোটি active user; post-এ ছবি আর video থাকতে পারে।

APIকাজ
POST /v1/me/feedPost publish; param: content, auth_token
GET /v1/me/feedনিজের news feed আনা; param: auth_token
11.2

Fanout: push বনাম pull

Fanout মানে একটা post সব বন্ধুর কাছে পৌঁছানো। কখন পৌঁছাবে, সেটাই প্রশ্ন।

Fanout on write (push)Fanout on read (pull)
কখনPost দেওয়ার সাথে সাথে সব বন্ধুর feed cache-এবন্ধু feed খুললে তখন
লাভFeed আগেই তৈরি, তাই পড়া খুব দ্রুতযে user আসে না তার জন্য কাজ হয় না; hotkey সমস্যা নেই
সমস্যাবহু বন্ধুওয়ালা user-এ hotkey সমস্যা; যারা আসেই না তাদের জন্যও কাজFeed খুলতে ধীর
নিজেকে যাচাই: কোটি follower-এর একজন celebrity-কে push দিলে কী হবে?

একটা post-এ কোটি cache write। Fanout queue আটকে যাবে, অন্যদের post-ও দেরিতে পৌঁছাবে। তাই celebrity-র জন্য pull।

11.3

Publish flow

  1. Web server authentication আর rate limiting করে (spam ঠেকাতে)।
  2. Post service post-টা DB আর post cache-এ রাখে।
  3. Fanout service graph DB থেকে বন্ধুদের ID আনে।
  4. User cache থেকে বন্ধুদের তথ্য এনে setting অনুযায়ী ছাঁকে (mute করা বন্ধু, নির্দিষ্ট লোকের সাথে share)।
  5. বন্ধুদের তালিকা আর post ID message queue-তে।
  6. Fanout worker queue থেকে নিয়ে news feed cache-এ <post_id, user_id> রাখে।
  7. Notification service বন্ধুদের জানায়।

Feed cache-এ পুরো user আর post object না রেখে শুধু ID রাখা হয়, নইলে memory খুব দ্রুত ফুরাবে। আর সংখ্যাটাও সীমিত: বেশিরভাগ user শুধু সাম্প্রতিক কয়েক হাজার post দেখে, তাই cache miss কম।

11.4

Retrieval ও cache layer

  1. User GET /v1/me/feed পাঠায়; load balancer থেকে web server।
  2. News feed service feed cache থেকে post ID-র তালিকা আনে।
  3. User cache আর post cache থেকে নাম, ছবি, content ইত্যাদি এনে পুরো feed সাজায় (hydrate)।
  4. JSON হিসেবে client-এ; ছবি আর video আসে CDN থেকে।
Cache layerকী রাখে
News feedপ্রতিটা user-এর feed-এর post ID
Contentপ্রতিটা post-এর data; জনপ্রিয় content আলাদা hot cache-এ
Social graphকে কাকে follow করে
Actionকে like, reply বা অন্য কিছু করেছে
CounterLike, reply, follower, following-এর সংখ্যা

Wrap up-এ বই বলে: database scaling (vertical বনাম horizontal, SQL বনাম NoSQL, master-slave replication, read replica, consistency model, sharding), stateless web tier, যতটা সম্ভব cache, একাধিক data center, message queue দিয়ে component আলাদা, আর QPS ও feed latency monitor করা।

নিজেকে যাচাই: feed cache-এ পুরো post object কেন রাখা হয় না?

একই post হাজার বন্ধুর feed-এ থাকে। পুরো object রাখলে হাজার copy। শুধু ID রাখলে content একবার post cache-এ থাকে, আর edit হলে এক জায়গাতেই বদলাতে হয়।
