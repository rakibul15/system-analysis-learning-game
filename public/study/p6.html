VOLUME 2 · CHAPTER 7

Hotel reservation system

Marriott-এর মতো hotel chain। QPS খুব কম, কিন্তু একটা ভুলে একই room দুজনকে বিক্রি। তাই এই chapter scale নিয়ে নয়, concurrency নিয়ে। একই সমস্যা: একটা delivery slot বা rider-এর capacity দুজন merchant-কে একসাথে দেওয়া।

7.1

Scope ও data

বইয়ের ধরে নেওয়া: ৫,০০০ hotel, ১০ লাখ room; booking-এর সময়ই পুরো payment; booking হয় room type ধরে (যেমন "deluxe king"), নির্দিষ্ট room নম্বর নয়; ১০% overbooking চলে (কেউ কেউ cancel করে); দাম দিনে দিনে বদলায়।

FunnelQPS
Hotel আর room-এর page দেখা≈ 300
Booking page≈ 30
Reservation সম্পন্ন≈ 3

Read বেশি, write কম, আর data-র গঠন পরিষ্কার; সবচেয়ে বড় কথা ACID লাগে। তাই relational DB। Inventory রাখা হয় room type আর তারিখ ধরে: room_type_inventory(hotel_id, room_type_id, date, total_inventory, total_reserved)। প্রতিটা তারিখের প্রতিটা room type-এর একটা row; ভবিষ্যতের ২ বছরের row আগেই বানিয়ে রাখা।

7.2

Double booking ও concurrency

দুই রকম double booking। একই user দুবার click করল: সমাধান idempotency key। Booking page load হওয়ার সময়ই একটা reservation_id তৈরি হয়; সেটাই primary key, তাই দ্বিতীয় submit unique constraint-এ আটকায়। দুই user একই শেষ room নিতে চায়: race condition।

উপায়কীভাবেভালোসমস্যা
Pessimistic lockSELECT … FOR UPDATE: পড়ার সময়ই row lock, অন্যরা অপেক্ষা করেসহজ, update-এ সংঘাত নেইDeadlock হতে পারে; লম্বা lock-এ scale হয় না
Optimistic lockversion column; লেখার সময় WHERE version = পড়া_মান, না মিললে retryLock নেই, দ্রুতঅনেকে একসাথে চাইলে বারবার fail আর retry
DB constraintCHECK (total_reserved <= total_inventory)সবচেয়ে সহজসব DB সমর্থন করে না; code থেকে logic আলাদা হয়ে যায়

বই optimistic lock নেয়, কারণ hotel-এ QPS কম আর একই room type-এ একসাথে অনেকে খুব কম চায়। Flash sale-এর মতো জায়গায় যেখানে হাজারজন একসাথে একটা জিনিস চায়, সেখানে optimistic lock-এ বারবার fail হয়।

নিজেকে যাচাই: ঈদের আগে একটা hub-এর pickup slot-এ একসাথে ৫০০ merchant booking দিচ্ছে। Optimistic lock কেন খারাপ হবে?

একজন ছাড়া সবার version মিলবে না, সবাই retry করবে, আবার একজন জিতবে। Retry-এর ঝড়ে DB-র চাপ আর latency দুটোই বাড়বে। এখানে pessimistic lock, অথবা slot-কে queue-তে সাজিয়ে একে একে দেওয়া ভালো।

7.3

Scale ও microservice

যদি QPS হাজার গুণ হয় (যেমন Booking.com): DB shard করুন hotel_id দিয়ে, কারণ প্রায় সব query একটা hotel-এর ভেতরে। Inventory Redis-এ cache করুন: বেশিরভাগ "room আছে?" প্রশ্ন cache থেকে উত্তর পায়। Cache আর DB একটু অমিল হতে পারে, কিন্তু চূড়ান্ত যাচাই DB-তে হয়, তাই ভুল booking হয় না।

Microservice-এ reservation আর inventory আলাদা service আর আলাদা DB হলে একটা transaction-এ দুটো বদলানো যায় না। উপায় 2PC বা Saga (Chapter 12-এ বিস্তারিত)। বইয়ের বাস্তববাদী পরামর্শ: reservation আর inventory একই relational DB-তে রাখুন, যাতে একটা ACID transaction-এই কাজ হয়। সব microservice-এর আলাদা DB থাকতেই হবে, এমন কোনো নিয়ম নেই।

Metadata ও deliverability

Email metadata-র access pattern: প্রায় সব query এক user-এর নিজের email নিয়ে, আর বেশিরভাগ সাম্প্রতিক। তাই data partition হয় user_id দিয়ে। Relational DB-তে বড় email body ভালো চলে না, তাই Bigtable-ধাঁচের NoSQL। Table emails_by_folder: partition key (user_id, folder_id), clustering key email_id (TIMEUUID, নতুন আগে)।

S3-ধাঁচের object storage

Part ৪-এ YouTube আর Google Drive-এ "blob storage" box এঁকেছি। এবার সেই box-এর ভেতর। Parcel-এর POD (proof of delivery) ছবি, invoice PDF সব এখানেই যায়।

9.1

Object storage কী

ধরনকীভাবে রাখেউদাহরণ
BlockRaw block, server-এ disk হিসেবে লাগানো; সবচেয়ে দ্রুতDatabase-এর disk, VM-এর volume

শব্দ: bucket (object রাখার পাত্র, নাম পৃথিবীজুড়ে unique), object, versioning, URI। বইয়ের লক্ষ্য: ১০০ PB data, durability ছয় ৯ (99.9999%), availability চার ৯ (99.99%)।

9.2

Data ও metadata আলাদা

মূল চিন্তাটা UNIX file system থেকে: file-এর নাম আর তথ্য (inode) এক জায়গায়, file-এর data আরেক জায়গায়। Object storage-এ metadata বদলায়, data বদলায় না। তাই দুটোকে আলাদা store-এ রেখে আলাদাভাবে scale।

Data store-এর ভেতরে: placement service ঠিক করে কোন data node-এ রাখবে (cluster-এর map রাখে, heartbeat নেয়, নিজে Paxos বা Raft-এ replicated)। Data routing service stateless, request ঠিক node-এ পাঠায়। একটা primary আর দুটো replica। সব replica লিখলে তবে সফল ধরলে consistency ভালো কিন্তু latency বেশি; শুধু primary লিখলে উল্টো।

ছোট object প্রতিটা আলাদা file হলে inode ফুরায় আর disk block অপচয় হয়। তাই অনেক ছোট object একটা বড় file-এ পরপর জোড়া (WAL-এর মতো), আর একটা lookup table: object_id → file_name, start_offset, size। প্রতিটা data node-এ এই table আলাদা RocksDB বা SQLite-এ।

9.3

Durability: replication বনাম erasure coding

Hard disk বছরে প্রায় 0.81% হারে নষ্ট হয়। তিনটা copy রাখলে durability প্রায় ছয় ৯। Copy আলাদা failure domain-এ (আলাদা availability zone) রাখতে হয়, যাতে একটা বিদ্যুৎ বিভ্রাটে সব না যায়।

৩ গুণ replicationErasure coding (8+4)
কীভাবেপুরো data-র তিনটা copyData ৮ টুকরো, তা থেকে ৪টা parity টুকরো; যেকোনো ৪টা হারালেও বাকি ৮টা থেকে পুরো data
বাড়তি জায়গা200%50%
Durabilityপ্রায় ছয় ৯আরও বেশি (প্রায় এগারো ৯)
পড়ার গতিদ্রুত, একটা copy থেকেইধীর, কয়েকটা node থেকে টুকরো জোড়া
জটিলতাসহজহিসাব আর recovery জটিল

Disk নষ্ট না হয়েও data নীরবে বদলে যেতে পারে (bit rot)। তাই প্রতিটা object আর প্রতিটা file-এর শেষে checksum (MD5, SHA1); পড়ার সময় মিলিয়ে দেখা, না মিললে অন্য replica থেকে।

নিজেকে যাচাই: ৫ বছরের পুরনো POD ছবি কেউ প্রায় দেখে না, কিন্তু রাখতেই হবে। কোনটা নেবেন?

Erasure coding। জায়গা অনেক কম লাগে আর durability বেশি; পড়া একটু ধীর হলেও ক্ষতি নেই, কারণ কেউ প্রায় পড়েই না। সাম্প্রতিক, ঘনঘন দেখা ছবিতে replication।

VOLUME 2 · CHAPTER 10

Real-time gaming leaderboard

Online game-এর top 10 player আর নিজের rank। ছোট chapter, কিন্তু একটা জরুরি শিক্ষা: সঠিক data structure বাছলে জটিল distributed design লাগে না। Rider-দের মাসিক performance বা delivery সংখ্যার ranking একই সমস্যা।

10.1

Scope ও SQL-এর সমস্যা

বইয়ের ধরে নেওয়া: top 10 দেখানো, user-এর নিজের rank আর তার উপরে-নিচে ৪ জন; প্রতিটা জেতা match-এ ১ point; প্রতি মাসে নতুন leaderboard; ৫০ লাখ DAU, আড়াই কোটি MAU, প্রতিজন দিনে ১০টা match। Score update QPS গড়ে ~৫০০, peak ~২,৫০০।

SQL-এ: SELECT … ORDER BY score DESC। Top 10 index দিয়ে চলে, কিন্তু "আমি কততম?" প্রশ্নে পুরো table sort বা আমার উপরের সবাইকে গুনতে হয়: লাখো row-এ কয়েক সেকেন্ড, আর score প্রতি মুহূর্তে বদলায় বলে cache-ও কাজে আসে না।

10.2

Redis sorted set

Sorted set প্রতিটা member-এর সাথে একটা score রাখে, সবসময় score অনুযায়ী সাজানো। ভেতরে দুটো জিনিস: member থেকে score খোঁজার hash table, আর সাজানো ক্রম রাখার skip list (linked list-এর উপর কয়েক স্তরের index, তাই খোঁজা O(log n))।

Payment system

Amazon-এর মতো e-commerce-এর checkout। দুই দিক: pay-in (buyer থেকে টাকা কোম্পানির কাছে) আর pay-out (কোম্পানি থেকে seller-কে)। Delivery-তে: COD সংগ্রহ হল pay-in, merchant payout হল pay-out। QPS কম (দিনে ১০ লাখ transaction ≈ ১০ TPS), কিন্তু সঠিকতা আর reliability সবার আগে।

11.1

Pay-in flow

API: POST /v1/payments (buyer info, checkout_id, payment orders; প্রতিটা order-এ seller, amount, currency, payment_order_id) আর GET /v1/payments/{id}। Amount string হিসেবে, floating point নয়: 0.1 + 0.2 ≠ 0.3 টাকার হিসাবে চলবে না। Database: relational, ACID সহ, আর বছরের পর বছর পরীক্ষিত; এখানে performance-এর চেয়ে নির্ভরযোগ্যতা বেশি দামি। প্রতিটা payment order-এর status: NOT_STARTED → EXECUTING → SUCCESS / FAILED।

11.2

Ledger ও double-entry

প্রতিটা transaction দুটো entry: একটা account থেকে debit, আরেকটায় সমান credit। সব entry-র যোগফল সবসময় শূন্য। কোথাও যোগফল না মিললে বোঝা যায় কিছু ভুল হয়েছে, আর প্রতিটা টাকার উৎস আর গন্তব্য শেষ পর্যন্ত খুঁজে পাওয়া যায়।

11.3

Retry, idempotency, exactly-once

টাকা ঠিক একবার কাটতে হবে। বই exactly-once-কে দুই ভাগে ভাঙে:

At-least-once = retry

Network-এ fail হলে আবার চেষ্টা। প্রতিবার অপেক্ষা বাড়ে (exponential backoff: ১, ২, ৪, ৮ সেকেন্ড …), যাতে বিপদগ্রস্ত server-এ আরও চাপ না পড়ে। বারবার fail হলে retry queue, শেষে dead letter queue-তে যায় হাতে দেখার জন্য।

At-most-once = idempotency

প্রতিটা request-এ একটা idempotency key (header-এ, সাধারণত UUID)। Server একই key আগে দেখলে নতুন করে কাটে না, আগের ফল ফেরত দেয়। DB-তে key-টা unique constraint, তাই দুটো একসাথে এলেও একটাই ঢোকে।

দুটো মিলে exactly-once। Service-দের মাঝে যোগাযোগ: synchronous HTTP সহজ, কিন্তু একটা service ধীর হলে পুরো chain আটকায়। বড় scale-এ asynchronous (Kafka): ledger, wallet, analytics নিজের গতিতে payment event পড়ে। Replication lag-এর কারণে replica থেকে পুরনো status পড়লে ভুল সিদ্ধান্ত, তাই payment status primary থেকে পড়া বা consensus-ভিত্তিক DB।

নিজেকে যাচাই: user "Pay" দুবার চাপল। Idempotency key না থাকলে আর থাকলে কী হবে?

না থাকলে server দুটো আলাদা payment ভেবে দুবার কাটবে। থাকলে দুটো request-এ একই key (key তৈরি হয় checkout-এর সময়, click-এর সময় নয়), দ্বিতীয়টা unique constraint-এ আটকায় আর প্রথমটার ফল ফেরত পায়।

VOLUME 2 · CHAPTER 12

Digital wallet

bKash বা Nagad-এর মতো: এক wallet থেকে আরেক wallet-এ টাকা পাঠানো। বইয়ের লক্ষ্য সেকেন্ডে ১০ লাখ transfer, ৯৯.৯৯% reliability, আর reproducibility: যেকোনো সময়ের balance শুরু থেকে আবার হিসাব করে বের করা যায়। এই chapter-এর তিনটা ধারণা (distributed transaction, event sourcing, CQRS) microservice architecture-এর প্রায় সব জায়গায় লাগে।

12.1

Scope ও সমস্যা

প্রতিটা transfer দুটো কাজ: A-র balance কমানো আর B-র বাড়ানো। সেকেন্ডে ১০ লাখ transfer এক database-এ সম্ভব নয়: প্রতিটা transfer-এ দুটো লেখা (debit, credit), তাই আসলে সেকেন্ডে ২০ লাখ operation। একটা সাধারণ relational DB node ~১,০০০ TPS ধরলে প্রায় ২,০০০টা node লাগে। তাই balance অনেক shard-এ ভাগ। এখন A আর B প্রায়ই আলাদা shard-এ। দুটো আলাদা database-এ একসাথে, হয় দুটোই হবে নয়তো কোনোটাই না: এটাই distributed transaction।

প্রথম চিন্তা Redis-এ in-memory balance: দ্রুত, কিন্তু durable নয়, আর দুই shard-এ atomic update নেই। মাঝপথে crash হলে A-র টাকা কাটল, B পেল না।

নিজেকে যাচাই: 2PC-তে prepare-এর পর coordinator crash করলে কী হয়?

12.3

Event sourcing ও CQRS

Reproducibility-র প্রশ্ন: শুধু বর্তমান balance রাখলে, balance ভুল হলে কেন ভুল তা জানা যায় না। Event sourcing-এ state নয়, ঘটনাগুলো রাখা হয়।

শব্দমানেউদাহরণ

যেহেতু event কখনও বদলায় না আর state machine deterministic, শুরু থেকে সব event আবার চালালে যেকোনো মুহূর্তের balance হুবহু পাওয়া যায়। Audit-এর জন্য এটা সোনা। প্রতিবার শুরু থেকে চালানো ধীর, তাই নিয়মিত snapshot।

CQRS (command query responsibility segregation): লেখার পথ (command → event) আর পড়ার পথ আলাদা। Event stream থেকে এক বা একাধিক read-only view বানানো হয় (যেমন balance দেখার view, মাসিক statement-এর view), প্রতিটা নিজের কাজের মতো করে। পড়ার view একটু পিছিয়ে থাকতে পারে (eventual consistency)।

Performance-এর জন্য বই command আর event local disk-এর file-এ (mmap), state RocksDB-তে রাখে, network hop এড়াতে। Reliability-র জন্য event list Raft দিয়ে কয়েকটা node-এ replicate। একাধিক Raft group-এ ভাগ করলে, group-দের মাঝে আবার TC/C বা Saga।

নিজেকে যাচাই: event sourcing-এ একটা ভুল transfer হয়ে গেলে event মুছে দেওয়া যায়?

না, event কখনও বদলায় বা মোছে না। ভুল ঠিক করতে একটা নতুন উল্টো event যোগ হয় (reversal)। ফলে ভুল আর সংশোধন দুটোই ইতিহাসে থাকে, ঠিক accounting-এর মতো।

Order book ও latency

Order book-এর data structure: প্রতিটা দামের স্তরে order-গুলোর doubly linked list (আগে আসা আগে মেলে), আর order_id থেকে list-এর node-এ সরাসরি যাওয়ার hash map। ফলে নতুন order যোগ, মেলানো আর cancel সব O(1)।

Latency কমানোর কৌশলকেন
Critical path-এর সব component এক server-এNetwork hop-এ প্রতিবার microsecond থেকে millisecond যায়
mmap-এর shared memory দিয়ে event busDisk আর network ছাড়াই process-দের মাঝে message
Single-threaded application loop, একটা CPU core-এ বাঁধাLock নেই, context switch নেই, তাই latency স্থির (p99 কম)
Event sourcingসব অবস্থা event থেকে আবার তৈরি করা যায়; recovery আর audit

High availability: একটা hot matching engine আর একটা warm; দুটো একই event stream পায়, warm শুধু ফল প্রকাশ করে না। Hot পড়লে warm সাথে সাথে দায়িত্ব নেয়। আরও শক্ত হলে Raft দিয়ে কয়েকটা server-এর cluster, যাতে leader পড়লে বাকিরা নিজেরাই নতুন leader বেছে নেয়। Fairness: market data সবাই একই সময়ে পায় তা নিশ্চিত করতে multicast; কিছু client exchange-এর পাশে নিজের server রাখে (colocation), যা আইনত অনুমোদিত সুবিধা। DDoS থেকে রক্ষায় public আর private service আলাদা, আর বারবার চাওয়া data cache।

নিজেকে যাচাই: বাকি সব chapter-এ horizontal scaling বলা হল। এখানে সব এক server-এ কেন?

লক্ষ্য throughput নয়, latency আর তার স্থিরতা। প্রতিটা network hop latency যোগ করে আর অনিশ্চয়তা বাড়ায়। আর ১০০টা symbol, প্রতিটার order book স্বাধীন, তাই symbol দিয়ে ভাগ করেই scale হয়, প্রতিটা symbol-এর ভেতরে নয়।
