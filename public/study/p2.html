CHAPTER 5

Consistent hashing

Horizontal scaling-এ data আর request অনেক server-এ সমানভাবে ভাগ করতে হয়। প্রশ্ন হল: server-এর সংখ্যা বদলালে কত key-কে জায়গা বদলাতে হবে? Consistent hashing সেই সংখ্যাটা ছোট রাখে।

5.1

Rehashing সমস্যা

সবচেয়ে সহজ উপায়: serverIndex = hash(key) % N, যেখানে N হল server-এর সংখ্যা। N স্থির থাকলে এটা ভালো চলে। কিন্তু একটা server পড়ে গেলে N বদলায়, আর প্রায় সব key-র index বদলে যায়।

key-র hash% 4 (চার server)% 3 (server 3 পড়ে গেল)ফল

পড়ে যাওয়া server-এ ছিল মাত্র ২টা key, কিন্তু সরল ৮টার মধ্যে ৬টা। Cache server হলে এর মানে: client ভুল server-এ খুঁজছে, একসাথে প্রচুর cache miss, আর সব চাপ database-এ।

নিজেকে যাচাই: modulo hashing কখন ঠিকঠাক কাজ করে?

যখন server pool-এর আকার স্থির আর data সমানভাবে ছড়ানো। Server যোগ বা বাদ হলেই সমস্যা।

5.2

Hash ring

Hash function-এর পুরো output range-কে (যেমন SHA-1-এ 0 থেকে 2160−1) দুই মাথা জুড়ে একটা বৃত্ত ভাবুন। Server-এর নাম বা IP hash করে তাকে বৃত্তে বসান। Key-কেও একই function দিয়ে বসান। এখানে modulo নেই। নিয়ম একটাই: key থেকে ঘড়ির কাঁটার দিকে গিয়ে প্রথম যে server পাবেন, key সেখানে থাকে।

5.3

Server যোগ ও বাদ

Server যোগ হলে

নতুন server থেকে ঘড়ির উল্টো দিকে আগের server পর্যন্ত যে key-গুলো আছে, শুধু সেগুলো নতুন server-এ আসে।

Server বাদ গেলে

বাদ যাওয়া server-এর key-গুলো ঘড়ির কাঁটার দিকে পরের server-এ যায়। অন্য কারও key নড়ে না।

সংজ্ঞাটা মুখস্থ রাখার মতো: hash table-এর আকার বদলালে গড়ে মাত্র k/nটা key সরাতে হয় (k = মোট key, n = slot বা server-এর সংখ্যা)। Modulo hashing-এ সরে প্রায় সব।

নিজেকে যাচাই: ১০ লাখ key আর ১০টা server। একটা server যোগ হলে মোটামুটি কত key সরবে?

প্রায় k/n, অর্থাৎ ১ লাখের কাছাকাছি। Modulo hashing-এ সরত প্রায় ৯ লাখ।

5.4

দুই সমস্যা ও virtual node

সাধারণ ring-এ দুটো সমস্যা থাকে। এক, server যোগ-বাদ হলে ring-এর ভাগগুলো সমান রাখা যায় না: কারও ভাগ খুব বড়, কারও খুব ছোট। দুই, key-গুলো সমানভাবে পড়ে না: একটা server-এ প্রচুর, অন্যটায় প্রায় কিছুই না।

সমাধান virtual node। প্রতিটা server ring-এ একবার নয়, অনেকবার বসে (s0_0, s0_1, s0_2 …)। ফলে প্রতিটা server অনেকগুলো ছোট ছোট ভাগের মালিক হয়, আর গড়ে সবার ভাগ কাছাকাছি আসে।

নিজেকে যাচাই: একটা server অন্যগুলোর চেয়ে দ্বিগুণ শক্তিশালী হলে কী করবেন?

তাকে বেশি virtual node দিন। Ring-এ তার ভাগ বাড়বে, তাই key-ও বেশি পাবে।

5.5

Wrap up

লাভকারণ
Server যোগ-বাদে কম key সরেশুধু পাশের ভাগটা প্রভাবিত হয়
Horizontal scaling সহজData মোটামুটি সমানভাবে ছড়ায়

বইয়ে যেসব ব্যবহার উল্লেখ আছে: Amazon Dynamo আর Apache Cassandra-র data partitioning, Discord chat, Akamai CDN, Google-এর Maglev load balancer।

CHAPTER 6

Key-value store

একটা distributed key-value store বানানো মানে distributed system-এর প্রায় সব বড় trade-off একসাথে দেখা। এই chapter-এর প্রতিটা অংশ একটা লক্ষ্য আর তার কৌশল।

6.1

Requirement ও এক server-এর সীমা

API মাত্র দুটো: put(key, value) আর get(key)। বইয়ের লক্ষ্য: ছোট key-value pair (10 KB-র নিচে), বিশাল data, high availability, high scalability, automatic scaling, tunable consistency, আর low latency।

এক server-এ সব memory-র hash table-এ রাখা সহজ, কিন্তু memory ফুরায়। Data compress করা আর শুধু বেশি ব্যবহৃত data memory-তে রেখে বাকিটা disk-এ রাখা কিছুটা সময় কেনে। তারপরও এক server একসময় ভরে যায়, তখন distributed হতেই হয়।

6.2

CAP theorem

তিনটা গুণ: Consistency (সব client একই সময়ে একই data দেখে), Availability (কিছু node পড়ে গেলেও প্রতিটা request উত্তর পায়), Partition tolerance (node-দের মাঝে network ছিঁড়ে গেলেও system চলে)। একসাথে তিনটা পাওয়া যায় না।

CP: consistency রাখি

n3 না ফেরা পর্যন্ত n1 আর n2-তে write বন্ধ, দরকারে error। Bank-এর balance-এর মতো জায়গায় এটাই লাগে: ভুল সংখ্যা দেখানোর চেয়ে অপেক্ষা ভালো।

AP: availability রাখি

সব node read-write নিতে থাকে, n3 পুরনো data দিতে পারে। Partition সারলে data মিলিয়ে নেওয়া হয়। Feed বা cart-এ এটা মানানসই।

নিজেকে যাচাই: parcel-এর live status দেখানোর service আর COD payment-এর হিসাব, কোনটায় কী নেবেন?

Status দেখানোয় AP চলে: কয়েক সেকেন্ড পুরনো status ক্ষতি করে না, কিন্তু page না খোলা করে। টাকার হিসাবে CP: ভুল balance দেখানোর চেয়ে সাময়িক error ভালো।

6.3

Partition ও replication

Data ভাগ হয় Chapter 5-এর consistent hashing দিয়ে। এতে server যোগ-বাদ হলে নিজে থেকেই ভাগ বদলায়, আর শক্তিশালী server বেশি virtual node পায় (heterogeneity)।

Replication-এর নিয়ম: key ring-এ যেখানে পড়ে, সেখান থেকে ঘড়ির কাঁটার দিকে প্রথম Nটা server-এ copy থাকে।

6.4

Quorum: N, W, R

N = replica-র সংখ্যা। W = write সফল ধরতে কতগুলো replica-র ack লাগবে। R = read সফল ধরতে কতগুলো replica-র উত্তর লাগবে। Coordinator client আর replica-দের মাঝে proxy হিসেবে কাজ করে।

Settingফল
R = 1, W = Nদ্রুত read
W = 1, R = Nদ্রুত write
W + R > NStrong consistency নিশ্চিত (সাধারণত N = 3, W = R = 2)
W + R ≤ NStrong consistency নিশ্চিত নয়
নিজেকে যাচাই: W + R > N হলে কেন সর্বশেষ data পাওয়া নিশ্চিত?

যে W-টা node-এ লেখা হয়েছে আর যে R-টা node থেকে পড়া হচ্ছে, তাদের মধ্যে অন্তত একটা node দুই দলেই থাকে। সেই node-এ সর্বশেষ লেখাটা আছে।

6.5

Versioning ও vector clock

Consistency model তিন রকম: strong (কোনো read কখনও পুরনো data পায় না), weak (পরের read নতুন মান না-ও পেতে পারে), eventual (যথেষ্ট সময় পেলে সব replica একই মানে পৌঁছায়)। Dynamo আর Cassandra eventual নেয়। তাতে দুই client একই key একসাথে বদলালে দুটো আলাদা version তৈরি হতে পারে।

Vector clock হল data-র সাথে জোড়া [server, version] pair-এর তালিকা। এটা দেখে বোঝা যায় একটা version অন্যটার পরে এসেছে, নাকি দুটো সমান্তরালে তৈরি (conflict)।

দুটো দাম আছে। Conflict মেলানোর logic client-কে লিখতে হয়। আর pair-এর তালিকা দ্রুত বড় হতে পারে, তাই একটা সীমা পেরোলে সবচেয়ে পুরনো pair বাদ দেওয়া হয়।

6.6

Failure সামলানো

আগে জানতে হবে node সত্যিই পড়েছে কি না। একজনের কথায় ভরসা নেই, কমপক্ষে দুটো স্বাধীন উৎস লাগে। সবাই সবাইকে heartbeat পাঠালে (all-to-all) server বেশি হলে খরচ অনেক। তাই gossip protocol।

সমস্যাকৌশলকীভাবে কাজ করে
Failure ধরাGossip protocolপ্রতিটা node নিজের heartbeat counter বাড়ায় আর কয়েকটা random node-কে তালিকা পাঠায়। কারও counter অনেকক্ষণ না বাড়লে তাকে offline ধরা হয়।
সাময়িক failureSloppy quorum + hinted handoffRing-এ প্রথম W বা R সংখ্যক healthy server নিয়ে কাজ চলে। পড়ে থাকা server-এর লেখা অন্য একটা server সাময়িকভাবে রাখে, সে ফিরলে ফেরত দেয়।
স্থায়ী failureAnti-entropy + Merkle treeReplica-দের data মেলানো হয়। Hash-এর tree তুলনা করে শুধু যে bucket আলাদা সেটাই sync হয়, পুরো data নয়।
Data center বিভ্রাটMulti-data-center replicationএকটা data center পুরো বন্ধ হলেও user অন্যটা থেকে data পায়।
নিজেকে যাচাই: Merkle tree কেন, সরাসরি সব key তুলনা করলে সমস্যা কী?

কোটি কোটি key একটা একটা করে তুলনা খুব ধীর আর network-খরুচে। Merkle tree-তে root hash মিললে সব ঠিক। না মিললে শুধু যে শাখা আলাদা, সেদিকে নামলেই হয়। Sync-এর data পার্থক্যের সমানুপাতিক হয়, মোট data-র নয়।

6.7

Write path ও read path

Architecture-এ কোনো master নেই। প্রতিটা node-এর দায়িত্ব একই (client API, failure detection, conflict resolution, replication), তাই single point of failure নেই। একটা node-এর ভেতরে write এভাবে চলে (Cassandra-র ধাঁচে):

Read path:

  1. আগে memtable দেখা হয়। থাকলে সেখান থেকেই উত্তর।
  2. না থাকলে bloom filter জিজ্ঞেস করা হয়: কোন SSTable-এ key থাকতে পারে।
  3. সেই SSTable থেকে data পড়ে client-কে ফেরত।
নিজেকে যাচাই: bloom filter না থাকলে কী হত?

Key কোন SSTable-এ আছে জানতে সবগুলো disk file একে একে খুঁজতে হত। Bloom filter "নিশ্চিত নেই" বলে দিতে পারে, তাই বেশিরভাগ file ছোঁয়াই লাগে না।

7.3

Snowflake

কৌশলটা divide and conquer: 64 bit-কে ভাগ করে প্রতিটা ভাগকে আলাদা দায়িত্ব দেওয়া।

ভাগBitকী ধারণ করেসীমা
Sign1ভবিষ্যতের জন্য রাখা, সবসময় 0—
Timestamp41একটা custom epoch থেকে কত millisecond গেছে241 ms ≈ ৬৯ বছর
Datacenter ID5কোন data center25 = 32
Machine ID5data center-এর কোন machine32 (প্রতি data center-এ)
Sequence12একই millisecond-এ একই machine-এর কততম ID; প্রতি ms-এ 0 থেকে শুরু212 = 4096 / ms

Datacenter আর machine ID startup-এ ঠিক হয় আর সাধারণত বদলায় না; বদলালে ID মিলে যাওয়ার ঝুঁকি। Timestamp আর sequence তৈরি হয় ID generator চলার সময়। তাত্ত্বিকভাবে একটা machine সেকেন্ডে ৪০ লাখের বেশি ID দিতে পারে (4096 × 1000), requirement-এর ১০,০০০-এর চেয়ে অনেক বেশি।

নিজেকে যাচাই: ৬৯ বছর পর কী হবে, আর সেটা কীভাবে পেছানো যায়?

41 bit ভরে গেলে timestamp আবার শূন্য থেকে শুরু হবে, ID-র ক্রম আর uniqueness ভাঙবে। Custom epoch যত সাম্প্রতিক নেবেন (১৯৭০ নয়, আপনার system চালুর তারিখ), তত দেরিতে ফুরাবে। ফুরানোর আগে নতুন epoch বা নতুন scheme-এ যেতে হয়।
