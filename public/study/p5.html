VOLUME 2 · CHAPTER 1

Proximity service

"আমার ৫ km-এর মধ্যে কোন কোন restaurant" (Yelp)। একই প্রশ্ন delivery-তে: pickup point-এর কাছের rider বা hub কোনগুলো। মূল সমস্যা: দুই dimension-এর (latitude, longitude) data-কে দ্রুত খোঁজার index।

1.1

Scope ও API

বইয়ের ধরে নেওয়া: user-এর location আর radius দিলে কাছের business; business owner যোগ, বদল, মুছতে পারে, কিন্তু সেটা real-time দেখানো লাগে না (পরের দিন চলে); latency কম; ১০ কোটি DAU, ২০ কোটি business।

হিসাব বা APIমান
Search QPS (দিনে প্রতিজন ৫ বার)100M × 5 ÷ 105 ≈ 5,000
GET /v1/search/nearbylatitude, longitude, radius (default 5 km)
/v1/businesses/{id}GET, POST, PUT, DELETE: business-এর তথ্য

Architecture-এ দুই service: location-based service (LBS), যা শুধু পড়ে, stateless, QPS বেশি; আর business service, যেখানে write কম আর বেশিরভাগ read business-এর page দেখা। Database primary-secondary: write primary-তে, read replica-য়। Replica-য় একটু দেরিতে পৌঁছানো চলে, কারণ business-এর তথ্য real-time লাগে না।

1.2

Grid থেকে geohash

সবচেয়ে সরল: WHERE lat BETWEEN … AND long BETWEEN …। Latitude আর longitude-এ আলাদা index থাকলেও প্রতিটা index একটা বিশাল set ফেরত দেয়, তারপর দুটোর intersection: ধীর। সমাধান হল দুই dimension-কে এক dimension-এ আনা।

উপায়কীভাবেসমস্যা
সমান gridপৃথিবীকে সমান মাপের ঘরে ভাগBusiness সমানভাবে ছড়ানো নয়: ঢাকার এক ঘরে হাজার, সমুদ্রের ঘরে শূন্য
Geohashপৃথিবীকে বারবার চার ভাগ; প্রতিটা ভাগ দুই bit; শেষে base32 stringBoundary সমস্যা (নিচে)

Boundary সমস্যা: খুব কাছের দুই জায়গার geohash-এ একটুও মিল না-ও থাকতে পারে (যেমন equator বা prime meridian-এর দুই পাশে), আবার একই prefix-এর দুই জায়গা আলাদা ঘরের ঠিক কিনারে থাকতে পারে। সমাধান: শুধু নিজের ঘর নয়, চারপাশের ৮টা ঘরও খোঁজা। যথেষ্ট business না পেলে geohash-এর শেষ অক্ষর বাদ দিয়ে বড় ঘরে খোঁজা।

নিজেকে যাচাই: user ঘরের একদম কোণে দাঁড়ানো। শুধু তার ঘর খুঁজলে কী ভুল হবে?

পাশের ঘরে ১০০ মিটার দূরের business বাদ পড়বে, অথচ নিজের ঘরের উল্টো কোণের ১ km দূরেরটা আসবে। তাই ৯টা ঘর (নিজের + ৮ প্রতিবেশী) খুঁজে তারপর দূরত্ব হিসাব করে ছাঁকা।

1.3

Quadtree ও তুলনা

Quadtree একটা in-memory tree: একটা ঘরে business বেশি হলে (যেমন ১০০-র বেশি) সেটাকে চার ভাগ, যতক্ষণ না প্রতিটা leaf-এ ১০০ বা কম। ফলে ঘন এলাকায় ঘর ছোট, ফাঁকা এলাকায় বড়। Database নয়: প্রতিটা LBS server startup-এ পুরো tree বানায়। ২০ কোটি business-এ memory লাগে প্রায় 1.7 GB, বানাতে কয়েক মিনিট।

আরেকটা উপায় Google S2: পৃথিবীর গোলককে Hilbert curve দিয়ে এক dimension-এ আনা; geofence-এর মতো কাজে ভালো, তবে interview-এ ব্যাখ্যা করা কঠিন।

GeohashQuadtree
বানানো ও ব্যবহারসহজ, tree লাগে নাTree বানাতে হয়, একটু জটিল
Radius দিয়ে searchভালোকম সরাসরি

নিজেকে যাচাই: rider-দের location প্রতি কয়েক সেকেন্ডে বদলায়। Quadtree ভালো নাকি geohash?

Geohash। Location বদলানো মানে শুধু একটা row-এর geohash বদলানো। Quadtree-তে প্রতিটা বদলে tree update জটিল আর ব্যয়বহুল। Quadtree মানায় স্থির data-য় (restaurant, hub)।

1.4

Storage, cache, scale

Geospatial index table: প্রতিটা row (geohash, business_id), compound key। এক geohash-এর সব business একটা JSON list-এ রাখলে update-এ পুরো list পড়তে-লিখতে হয় আর lock লাগে; আলাদা row-এ সহজ। পুরো table মাত্র কয়েক GB, এক server-এর memory-তে ধরে, তাই sharding নয়, শুধু read replica বাড়ানো।

CacheKey → value
Geohashgeohash → [business_id…], তিন precision-এর (4, 5, 6) জন্য আগেই হিসাব করা
Businessbusiness_id → business object

LBS বিভিন্ন region আর availability zone-এ, যাতে user কাছের server পায় আর কোনো দেশের data-নিয়ম মানা যায়। সময় বা ধরন দিয়ে filter (যেমন "এখন খোলা") পরে করা হয়, কারণ কয়েকটা geohash-এর business সংখ্যায় অল্প।

VOLUME 2 · CHAPTER 2

Nearby friends

Proximity service-এ business নড়ে না; এখানে সবাই নড়ে, আর location কয়েক সেকেন্ডে বদলায়। প্রশ্ন বদলে যায়: কাকে খুঁজব না, কাকে কখন জানাব। Merchant-এর app-এ assigned rider-এর live location দেখানো ঠিক এই সমস্যা।

2.1

Scope ও হিসাব

বইয়ের ধরে নেওয়া: যে বন্ধুরা অনুমতি দিয়েছে, ৫ মাইলের মধ্যে থাকলে তাদের দূরত্ব আর শেষ update-এর সময়; তালিকা কয়েক সেকেন্ড পরপর update; ১০ মিনিট inactive হলে তালিকা থেকে বাদ; location history রাখা। ১০ কোটি DAU, একসাথে ১০% অর্থাৎ ১ কোটি, প্রতি ৩০ সেকেন্ডে location।

হিসাবকীভাবেফল
Location update QPS10M ÷ 30≈ 334,000
2.2

WebSocket + Redis pub/sub

প্রতিটা user-এর একটা Redis pub/sub channel। User নিজের channel-এ location publish করে। তার প্রতিটা online বন্ধুর WebSocket connection-এর handler সেই channel-এ subscribe করা। Channel খুব সস্তা: subscriber না থাকলে প্রায় কোনো খরচ নেই।

নিজেকে যাচাই: দূরত্ব হিসাব publisher-এর server-এ না করে subscriber-এর handler-এ কেন?

প্রতিটা subscriber-এর নিজের সর্বশেষ location তার নিজের handler-এর কাছে আছে। Publisher-এর server-কে সব বন্ধুর location জানতে হলে প্রতিবার cache থেকে আনতে হত।

2.3

Scale ও সমস্যা

অংশBottleneckসমাধান
Redis pub/subMemory নয় (~200 GB, দুটো 100 GB-এর server-এই ধরে); আসল চাপ CPU: প্রতিটা update গড়ে ~৪০ জন online বন্ধুকে (৪০০ বন্ধুর ১০%), অর্থাৎ সেকেন্ডে ~১৪ million pushএক server সেকেন্ডে ~১ লাখ push ধরলে অন্তত ~১৪০টা Redis server; channel ভাগ consistent hashing দিয়ে; hash ring থাকে service discovery-তে (etcd, Zookeeper)
Pub/sub resizeServer যোগ-বাদে অনেক channel সরে, subscriber-দের আবার subscribe করতে হয়, CPU spikeকম traffic-এর সময় resize; শুরু থেকেই কিছু বেশি ক্ষমতা

অনেক বন্ধুর userHotspotবন্ধুর সংখ্যায় সীমা (যেমন ৫,০০০); subscriber-রা বিভিন্ন server-এ ছড়ানো

বন্ধু যোগ হলে নতুন channel-এ subscribe, বাদ দিলে unsubscribe। অচেনা কাছের মানুষ দেখানোর feature চাইলে user-এর বদলে প্রতিটা geohash-এর একটা channel, আর user নিজের ও আশপাশের ঘরের channel-এ subscribe।

Google Maps

তিনটা feature: user-এর location update, navigation (ETA সহ), আর map দেখানো। Rider-এর route, delivery-র ETA আর traffic-এ পথ বদলানো সব এখানে।

3.2

তিন service

Tile দুই রকম: raster (ছবি) আর vector (path আর polygon, client আঁকে)। Vector compress ভালো হয়, আর zoom করার সময় মসৃণ, কারণ ছবি টেনে বড় করা হয় না।

নিজেকে যাচাই: map tile কেন CDN-এ, server-এ বানিয়ে পাঠানো হয় না?

একই এলাকার একই zoom-এর tile সবার জন্য এক, আর খুব কম বদলায়। আগে বানিয়ে CDN-এ রাখলে কাছের edge থেকে দ্রুত আসে, server-এ কোনো হিসাব লাগে না।

3.3

Adaptive ETA ও rerouting

Navigation চলাকালীন traffic বদলালে চলমান user-দের ETA আর route update করতে হয়। সমস্যা: কোন traffic বদল কোন কোন user-কে প্রভাবিত করে, সেটা দ্রুত বের করা। Server প্রতিটা চলমান user-এর route-এর routing tile-গুলো রাখে, ছোট থেকে বড় স্তর পর্যন্ত। কোনো tile-এ traffic বদলালে শুধু যাদের route ওই tile ছুঁয়েছে তাদের update হয়।

Client-কে জানানোর উপায়: mobile push notification-এর payload ছোট আর web-এ চলে না, তাই WebSocket (অথবা server-sent events)। বই WebSocket নেয়।

নিজেকে যাচাই: rider-এর ETA শুধু রাস্তার দূরত্ব ÷ গড় গতি দিয়ে হিসাব করলে কী ভুল হবে?

Traffic, সময় (অফিস টাইম বনাম রাত), আর আগের দিনের একই সময়ের pattern বাদ যায়। এই কারণে ETA service আলাদা: real-time traffic আর historical data নিয়ে ML model।

VOLUME 2 · CHAPTER 4

Distributed message queue

Part ১ থেকে বারবার "message queue" box এঁকেছি। এবার box-এর ভেতরটা: Kafka-র মতো একটা system। বইয়ের লক্ষ্য: data দুই সপ্তাহ রাখা, একই message বারবার পড়া যায়, partition-এর ভেতরে ক্রম ঠিক, delivery semantics বেছে নেওয়া যায়, throughput বা latency কোনটা বেশি দরকার সেটা tune করা যায়, data disk-এ আর replicated।

4.1

Model ও শব্দ

Point-to-point

একটা message শুধু একজন consumer পড়ে, পড়া হলে queue থেকে মুছে যায়।

Publish-subscribe

Message একটা topic-এ যায়, topic-এর সব subscriber পড়ে। Kafka-ধাঁচের system দুটোই দেয় consumer group দিয়ে।

নিজেকে যাচাই: একটা group-এ partition ৩টা কিন্তু consumer ৫ জন। কী হবে?

৩ জন একটা করে partition পাবে, ২ জন বসে থাকবে। এক group-এর ভেতরে partition-এর সংখ্যাই parallelism-এর সীমা। তাই বেশি consumer চাইলে আগে partition বাড়াতে হয়।

4.2

Storage ও batching

Message queue-তে read আর write দুটোই ভারী, update বা delete প্রায় নেই, আর access sequential। তাই database নয়, write-ahead log (WAL): শুধু শেষে যোগ করা একটা file। Partition-এর log segment-এ ভাগ: নতুন message শুধু active segment-এ যায়, ভরা segment শুধু পড়া হয়, retention শেষে মুছে যায়। Disk-এ sequential পড়া-লেখা খুব দ্রুত, random access-এর চেয়ে অনেক বেশি, তাই disk-ভিত্তিক হয়েও throughput বেশি।

Message-এর গঠন: key, value, topic, partition, offset, timestamp, size, CRC (data নষ্ট হয়নি যাচাই)। Producer থেকে broker থেকে consumer পর্যন্ত message একই format-এ থাকে, তাই মাঝে copy বা রূপান্তর লাগে না।

Batching সব জায়গায়: producer কয়েকটা message জমিয়ে একসাথে পাঠায়, broker একসাথে disk-এ লেখে, consumer একসাথে আনে। Batch বড় হলে throughput বাড়ে, কিন্তু latency-ও বাড়ে, কারণ প্রথম message batch ভরার জন্য অপেক্ষা করে। এটাই tune করার জায়গা।

4.3

Producer, consumer, rebalance

Producer-এর ভেতরে একটা routing layer থাকে: কোন partition-এর leader কোন broker-এ, সেটা জেনে সরাসরি সেখানে পাঠায়, আর buffer-এ batch বানায়। আলাদা proxy server রাখলে একটা network hop আর latency বাড়ত।

Push (broker পাঠায়)

Latency কম। কিন্তু consumer ধীর হলে চাপে পড়ে যায়, আর broker-কে প্রতিটা consumer-এর গতি জানতে হয়।

Pull (consumer আনে) · বইয়ের পছন্দ

Consumer নিজের গতিতে আনে, পিছিয়ে পড়লে ধরে ফেলতে পারে, batch-এ আনা সহজ। দাম: message না থাকলে খালি ঘোরা, তাই long polling।

Rebalance: প্রতিটা group-এর একটা coordinator (একটা broker) থাকে। Consumer heartbeat পাঠায়। কেউ যোগ হলে, চলে গেলে বা heartbeat বন্ধ হলে coordinator partition আবার ভাগ করে। কতদূর পড়া হয়েছে (committed offset) সেটা একটা state store-এ থাকে, যাতে নতুন consumer ঠিক সেখান থেকে শুরু করে। Broker আর topic-এর metadata থাকে Zookeeper-এর মতো জায়গায়।

4.4

Replication ও delivery semantics

প্রতিটা partition-এর কয়েকটা replica আলাদা broker-এ: একটা leader (সব read-write এখানে), বাকিরা follower। In-sync replica (ISR) হল যে follower-রা leader-এর সাথে তাল রেখে চলছে। Producer-এর ACK setting ঠিক করে কতটা নিরাপদ:

ACKকখন সফলফল

নিজেকে যাচাই: consumer message process করল, offset commit করার আগে crash। At-least-once-এ কী হবে?

Commit হয়নি, তাই নতুন consumer একই message আবার পাবে আর আবার process করবে। এই কারণে consumer idempotent হওয়া দরকার, যেমন "parcel X delivered" দুবার এলেও status একবারই বদলায়।

VOLUME 2 · CHAPTER 5

Metrics monitoring ও alerting

CPU, memory, request rate, error rate দেখা আর গোলমালে alert। Part ১-এর logging-metrics অংশের ভেতরের design। বইয়ের লক্ষ্য: কোম্পানির ভেতরের system, হাজার server pool, প্রতিটায় ১০০ machine, প্রতিটা machine-এ ~১০০ metric, অর্থাৎ প্রায় ১ কোটি metric।

5.1

Scope ও data model

Retention: raw data ৭ দিন, তারপর ১ মিনিটের resolution-এ ৩০ দিন, তারপর ১ ঘণ্টার resolution-এ ১ বছর। পাঁচ অংশ: data collection, transmission, storage, alerting, visualization।

Data model হল time series: একটা metric-এর নাম, কয়েকটা label (key-value), আর (timestamp, value)-এর ধারা। যেমন cpu.load host=web-01,region=dhaka 1730000000 0.42। Write খুব ভারী আর স্থির; read হঠাৎ হঠাৎ (dashboard খোলা বা alert-এর query)।

General-purpose database এই চাপে ভালো চলে না আর time-series query (moving average, এক মিনিটের গড়) লেখাও কঠিন। তাই time-series database: InfluxDB, Prometheus, OpenTSDB। এগুলো label দিয়ে index করে, তাই label-এর মানের সংখ্যা (cardinality) কম রাখা জরুরি।

VOLUME 2 · CHAPTER 6

Ad click event aggregation

প্রতিটা ad click গোনা, প্রতি মিনিটে। এই সংখ্যা দিয়ে advertiser-কে bill করা হয়, তাই সঠিকতা সবচেয়ে বড় শর্ত। একই ধাঁচ: প্রতি মিনিটে কোন hub-এ কত parcel ঢুকল, বা merchant-ভিত্তিক COD-র হিসাব।

6.1

Scope ও data

Query তিনটা: গত M মিনিটে একটা ad-এ কত click; প্রতি মিনিটে সবচেয়ে বেশি click পাওয়া ১০০টা ad; দেশ, IP, user_id-র মতো attribute দিয়ে filter। দিনে ১০০ কোটি click, ২০ লাখ ad। দেরিতে আসা আর duplicate event সামলাতে হবে। End-to-end latency কয়েক মিনিট চলে।

হিসাবফল
গড় QPS≈ 10,000
Peak QPS (৫ গুণ ধরে)≈ 50,000
Raw data, দিনে (প্রতিটা 0.1 KB)≈ 100 GB

Raw data নাকি aggregated, কোনটা রাখব? দুটোই। Raw থাকে backup হিসেবে: কোনো bug হলে বা হিসাব নতুন করে করতে হলে। Query চলে aggregated data-য়, কারণ raw-এ query খুব ধীর। Write-heavy আর সময়-ভিত্তিক, তাই Cassandra বা InfluxDB।

6.2

Pipeline

Batch আর streaming আলাদা করে চালানোর নাম lambda architecture: দুটো codebase রাখতে হয়। বই kappa architecture নেয়: একটাই streaming pipeline, আর হিসাব নতুন করে করতে হলে raw data একই pipeline দিয়ে আবার চালানো।

6.3

Time, window, watermark

Event time

Click যখন হয়েছিল (client-এর সময়)। হিসাব বেশি সঠিক, কিন্তু client-এর ঘড়ি ভুল হতে পারে, আর event দেরিতে আসে। বইয়ের পছন্দ।

Processing time

Server যখন event পেল। সহজ আর নির্ভরযোগ্য ঘড়ি, কিন্তু দেরিতে আসা event ভুল মিনিটে গোনা হয়।

Watermark: window শেষ হওয়ার পরও কিছুক্ষণ (যেমন ১৫ সেকেন্ড) খোলা রাখা, যাতে একটু দেরিতে আসা event ধরা পড়ে। লম্বা watermark বেশি সঠিক কিন্তু latency বাড়ায়। খুব দেরিতে আসা অল্প কিছু event তবুও বাদ যায়; সেগুলো দিনের শেষে reconciliation-এ ঠিক হয়।

6.4

Exactly-once ও সঠিকতা

এখানে duplicate মানে advertiser-কে বেশি bill, আর হারানো মানে কম। তাই at-least-once যথেষ্ট নয়। Duplicate আসে দুই জায়গা থেকে: client একই event দুবার পাঠায় (fraud বা retry), আর server crash হলে offset commit-এর আগের event আবার আসে।

সমাধান: aggregation node offset বাইরের storage-এ (HDFS, S3) রাখে। Downstream (queue 2) ack দিলে তবেই offset এগোয়। "ফল পাঠানো" আর "offset সংরক্ষণ" একই distributed transaction-এ, যাতে দুটোই হয় বা কোনোটাই না।

নিজেকে যাচাই: streaming pipeline সঠিক হলে দিনের শেষে আবার batch-এ গোনা কেন?

Watermark-এর পরে আসা event, code-এর bug, বা কোনো অজানা failure streaming-এর ফল সামান্য ভুল করতে পারে। টাকার হিসাবে "সামান্য" চলে না। Raw data থেকে আলাদা পথে গুনে মেলালে ভুল ধরা পড়ে। COD settlement-এ ঠিক এই কারণে দিনের শেষে reconciliation হয়।
